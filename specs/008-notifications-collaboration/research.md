# Research: Notifications and Collaboration

**Feature**: 008-notifications-collaboration | **Date**: 2026-09-01 | **Status**: Complete

No `NEEDS CLARIFICATION` remained — all technical choices are informed by `draft/libraries/buildingblocks.md` + constitution Principles XVII/XIX + existing modules `Notifications` stub + producer contracts `Projects.Contracts`/`Documents.Contracts`/`AiProcessing.Contracts` + `BuildingBlocks.ServiceDefaults` OTel. `Email` is future stub per spec; research resolves channel abstraction, not provider selection.

## Decision 1: Event-driven generation isolated in BC-09 — `NotificationDispatcher` consumes integration events, no logic in producers

- **Decision**: `NotificationDispatcher` lives in `Notifications.Infrastructure` and implements `IIntegrationEventHandler<T>` for each producer event type (`WorkItemAssignedIntegrationEvent` from `Projects.Contracts`, `DocumentApprovedIntegrationEvent`/`DocumentUploadedIntegrationEvent`/`DocumentClassifiedIntegrationEvent` from `Documents.Contracts`, `LlmResultGeneratedIntegrationEvent`/`LlmOperationQueuedIntegrationEvent` + `RagQueryExecutedIntegrationEvent` for `AiReviewRequested` from `AiProcessing.Contracts`, plus `RiskIncreasedIntegrationEvent` from `Metrics`/`Projects` when available). Registration is `builder.Services.AddRabbitMqEventBus(...).AddSubscription<WorkItemAssignedIntegrationEvent, NotificationDispatcher>()...` (one dispatcher type handling many event types via explicit per-type wrappers or `IIntegrationEventHandler<IntegrationEvent>` dispatch by runtime type — chosen: per-type thin adapter that forwards to `NotificationDispatcher.HandleAsync(IntegrationEvent, CancellationToken)` to keep consumer ack/ retry per-topic). Producers (`Projects`, `Documents`, `AiProcessing`) emit integration events via their own `AppDbContextBase` outbox (`IOutboxWriter.StageAsync`) — they do **not** inject `Notifications` services nor create `Notification` aggregates. `NotificationsDbContext` never shares a transaction with producer `DbContext`; correlation is via `IntegrationEvent.Id` + `TenantId` + `OccurredOnUtc`.
- **Rationale**: Satisfies R1 (notifications derived ONLY from integration events, no logic inside other contexts) + Principle V (modular ownership — BC-09 isolated, cross-module only via `BuildingBlocks.EventBus`) + Principle XVII (async via outbox + RabbitMQ, at-least-once, handlers idempotent). Reuses existing BuildingBlocks outbox pattern proven in 005/006/007. Keeps producer tests unaffected — adding a notification never changes producer behavior or adds coupling.
- **Alternatives considered**: Direct in-process `IDomainEventHandler` subscription from `Notification` to producer `DomainEvent` inside same `DbContext` (rejected — would require `NotificationsDbContext` to share process/schema with producers, violates BC isolation, and producer unit tests would need `Notifications` registration). Polling producer tables for changes (rejected — violates event-driven, adds latency, duplicates producer persistence model access). CDC `Debezium` from producer outbox (rejected — outbox already has `OutboxProcessor` publishing to RabbitMQ; CDC adds infra).
- **ADR**: `ADR-008-01` records event-driven isolation, subscription list `WorkItemAssigned|Reassigned|Overdue|Blocked|Completed|ReviewRequested|DocumentUploaded|Classified|Approved|AiReviewRequested|RiskIncreased` → `NotificationType`, and that producers are never modified for notification delivery.

## Decision 2: Deduplication/idempotency via persistence `UNIQUE(SourceEventId, RecipientId, Channel)` + application catch of `23505` (no separate dedupe table)

- **Decision**: `notifications.notifications` table has `UNIQUE(SourceEventId, RecipientId, Channel)` (covers per-channel dedupe; spec `DedupeKey = eventId + recipient` extended with `Channel` per FR-006 `+ optionally Channel`). `NotificationDispatcher.HandleAsync` for each recipient does: (1) evaluate `INotificationPolicy.IsEnabled` (preference×policy) — if skipped, insert `DeliveryState=SkippedByPreference|SkippedByPolicy`? or skip insert entirely? chosen: skip insert entirely (no row) but log `Skipped` via structured trace with `dedupeKey` + `reason` so no row bloat; alternative rows for skipped are not queryable but observability via log is sufficient; if audit needed later, `Skipped` rows can be enabled without breaking inbox. (2) Build `Notification` via `Notification.Create(recipientId, sourceEventId, type, channel, content, link, tenantId)` which validates `CheckRule(new DedupeKeyRequiredRule(sourceEventId, recipientId))`. (3) `await notifications.AddAsync(notification, ct); await unitOfWork.SaveChangesAsync(ct)` inside same `NotificationsDbContext` transaction as domain event `NotificationCreated` staging via `IOutboxWriter` if needed. (4) On `DbUpdateException` with inner `PostgresException.SqlState=="23505"` (unique violation), handler **swallows** and returns success (already-delivered, idempotent) — no retry, no `Failed` state. Concurrent storm of 10 redeliveries for same `eventId+recipient+channel` results in 1 row + 9 swallowed duplicates (race handled by DB, not application lock). `NotificationConsumed` concept is the `notifications` row itself — no separate `notification_consumed_events` table needed because granularity is per-recipient per-channel, not per-event globally.
- **Rationale**: Satisfies R3 (at-least-once, duplicate events do not produce duplicates) + Principle XVII (handlers MUST be idempotent) + SC-002 0% duplicate under 10× redelivery. `UNIQUE` at persistence is the strongest guarantee (stronger than application `SELECT before INSERT` which races). Swallowing `23505` keeps handler idempotent without extra `SELECT ... FOR UPDATE` on dedupe key before insert (which would add round-trip and still race without serializable isolation). Per-recipient per-channel dedupe is required — one event targeting 2 recipients must produce 2 rows (`evt-123+Alice+InApp`, `evt-123+Bob+InApp` distinct); per-channel dedupe allows `InApp` + `Email` to each have their own row without false dedupe (`evt-123+Alice+InApp` vs `evt-123+Alice+Email` distinct).
- **Alternatives considered**: Application `SELECT 1 FROM notifications WHERE SourceEventId=@e AND RecipientId=@r AND Channel=@c` before insert (rejected — races under concurrent consumers without `SERIALIZABLE` or advisory lock; requires extra query). Separate `notification_dedupe(SourceEventId,RecipientId,Channel) PK` table idempotency (rejected — duplicates the unique constraint that already exists on `notifications` itself; adds table + transaction). `INSERT ... ON CONFLICT DO NOTHING` via raw SQL (considered — equivalent to `23505` catch but EF Core `AddAsync` + `SaveChangesAsync` with catch keeps repository abstraction pure; raw SQL bypasses `EfRepository` and domain invariants). Chose EF `23505` catch kept inside `INotificationDeduplicationService` shim if EF exception parsing is needed.
- **ADR**: `ADR-008-02` records dedupe key `(SourceEventId,RecipientId,Channel)`, no separate dedupe table, swallow `23505` = success, and that skipped-by-preference produces no row (log only) — with note that per-channel rows enable independent `Email` retry without touching `InApp`.

## Decision 3: Channel abstraction via `IChannelRouter` → `IChannel` (fan-out, failure isolation, extensible, Email stub in v1)

- **Decision**: `IChannel` abstraction `Task<Result> DeliverAsync(Notification notification, CancellationToken ct)` with `Channel Channel { get; }`. Implementations: `InAppChannel : IChannel` (`Channel.InApp`, persists `Notification` row — actually `Notification` is persisted **before** channel fan-out? chosen: `Notification` is the `InApp` delivery itself — `InAppChannel.DeliverAsync` does nothing beyond ensuring the row exists; but to keep abstraction uniform, `NotificationDispatcher` first persists `Notification` with `DeliveryState=Pending` per channel, then calls `channel.DeliverAsync`; `InAppChannel` transitions `DeliveryState→Delivered` in same transaction; `EmailChannel` is stub that logs `Would send email to {RecipientId} subject={Title} link={Link}` and returns `Result.Success()` when enabled, or `Result.Failure` when configured to fail for test). `IChannelRouter { IReadOnlyList<IChannel> EnabledChannels(); Task FanOutAsync(Notification notification, CancellationToken ct); }` loops channels sequentially, `try { await channel.DeliverAsync(notification, ct) } catch (Exception ex) { Log.Error(ex, "Channel {Channel} failed for notification {NotificationId} type {Type}", channel.Channel, notification.Id, notification.Type); /* record DeliveryState=Failed for that channel without rolling back other channels */ }` — each channel has its own `DeliveryState` column per-channel? chosen: single `Channel` per `Notification` row — fan-out is modeled as one row per `(SourceEventId,RecipientId,Channel)` so per-channel `Failed` does not affect the other channel's row; dispatcher creates one `Notification` aggregate per enabled channel per recipient (so 1 event × 2 recipients × 2 channels = 4 rows). Failure in `Email` (`DeliveryState=Failed` row persisted) is observable via `notification_delivery_failed_total` log + column `DeliveryState=Failed` queryable, while `InApp` row stays `Delivered`. Extensibility: adding `PushChannel : IChannel` requires only `services.AddSingleton<IChannel, PushChannel>()` and `IChannelRouter` picks it up via `IEnumerable<IChannel>` DI — no dispatcher modification (verifies SC-007 via integration test adding `TestChannel`).
- **Rationale**: Satisfies R2 (`InApp` default + `Email` future + extensible abstraction, failure never blocks others) + SC-003 100% `InApp` when `Email` fails + SC-007 extensibility. Per-channel row matches spec FR-007 `Channel implementations subscribe to notification integration events; failure in one channel never blocks others` at data level. Uniform `IChannel` keeps testing easy — `EmailChannel` stub can be swapped for a throwing fake in `ChannelFanOutTests` without DB.
- **Alternatives considered**: Single `Notification` row with `DeliveryStates` jsonb `{ InApp: Delivered, Email: Failed }` (rejected — denormalizes channel state into one row, complicates dedupe per-channel and query for failed deliveries; per-channel row is cleaner and dedupe already per-channel). Message-bus fan-out where each channel is a separate RabbitMQ subscriber to `notifications.*` (considered — would decouple further but doubles infrastructure; spec Application Layer says `NotificationDispatcher` → channels + `EmailChannelConsumer` background, so in-process `IChannelRouter` with stub is sufficient for MVP; bus-level fan-out can be introduced behind `IChannelRouter` without changing dispatcher). Synchronous email send inside dispatcher transaction (rejected — would block `InApp` on SMTP latency/failure; violates R2).
- **ADR**: `ADR-008-03` records channel abstraction `IChannel`/`IChannelRouter`, per-channel row model, failure isolation via try/catch per channel + `DeliveryState=Failed` observable, and that `EmailChannel` is stub in v1 documenting future `SMTP`/`Graph` provider selection as non-blocking.

## Decision 4: Preferences as `NotificationPreference` aggregate + `INotificationPolicy` merge (policy mandates override user opt-out)

- **Decision**: `NotificationPreference` aggregate root keyed by `UserId` (`StronglyTypedId<Guid>`), `Preferences` stored as `jsonb` `Dictionary<int,Dictionary<int,bool>>` where outer key is `NotificationType` id, inner key is `Channel` id, value is `enabled` bool. Aggregate has `RowVersion` (`IsConcurrencyToken` bytea) for optimistic concurrency on `UpdatePreferences` (concurrent `PUT /preferences` returns 409 `Error.Conflict`). Command `UpdatePreferencesCommand(UserId, Dictionary<NotificationType,Dictionary<Channel,bool>> Preferences, byte[]? ExpectedRowVersion)` validates via `UpdatePreferencesValidator` (must reference valid `NotificationType`/`Channel` enumerations → 400, no unknown types allowed, `Enabled` is bool, gaps are treated as unset → defaults to provider). Domain service `INotificationPolicy` has `bool IsEnabled(NotificationType type, Channel channel, Guid userId, IReadOnlyDictionary<NotificationType,Dictionary<Channel,bool>> userPrefs)` and `IReadOnlySet<(NotificationType,Channel)> MandatedTypes`. Implementation `NotificationPolicy` (in `Notifications.Infrastructure`) loads `mandated` from config `Notifications:MandatedTypes` (default `WorkItemOverdue.InApp`, `WorkItemBlocked.InApp`, `RiskIncreased.InApp` per spec assumption) or from future `notification_policies` table/ org policy service (interface-ready, config-backed for MVP). Merge logic: `if (MandatedTypes.Contains((type,channel))) return true; // policy overrides` `if (userPrefs.TryGetValue(type, out var channelMap) && channelMap.TryGetValue(channel, out var enabled)) return enabled;` `return DefaultEnabled(type,channel)` where `DefaultEnabled` is `true` for `InApp` for all types (spec: new users all `InApp` enabled) and `false` for `Email` until opt-in. `NotificationPreference` default when no row exists is empty map (all defaults). Query `GetPreferencesQuery` returns merged view? chosen: `GetPreferences` returns raw user prefs + effective (merged) for UI to show mandated cannot-disable (UI disables toggle).
- **Rationale**: Satisfies R4 (per-user preferences `type×channel` within org policy limits) + SC-005 (disabled non-mandated → 0, mandated → 100% despite opt-out) + Principle VI (pure domain merge, testable via unit `PolicyMergeTests`). `jsonb` keeps schema stable when new `NotificationType` added (no column addition). `RowVersion` satisfies Constitution concurrency for mutable resource `NotificationPreference`. Config-backed `MandatedTypes` satisfies extensible without code change (adding a type to config or future DB table does not require code).
- **Alternatives considered**: Column-per-type `bool WorkItemAssignedInApp` etc. (rejected — requires migration per new type, not extensible). Separate `notification_preferences` row per `(UserId,Type,Channel)` triple (considered — normalized but requires 11×2 rows per user and join; jsonb is simpler for MVP, query is `UserId` PK lookup, not filtered by type). Policy as DB table `notification_mandated_policies(TenantId, NotificationType, Channel, IsMandated)` (future — chosen interface `INotificationPolicy` abstracts storage, config fallback satisfies MVP without new table; table can be added later behind same interface). Default `false` for all (rejected — spec says new users all `InApp` enabled by default).
- **ADR**: `ADR-008-04` records `NotificationPreference` jsonb + `RowVersion`, `INotificationPolicy` merge `policy overrides → preference else default`, default `InApp=true` `Email=false`, and that `MandatedTypes` default is `WorkItemOverdue.InApp`+`WorkItemBlocked.InApp`+`RiskIncreased.InApp` subject to follow-up org policy ADR.

## Decision 5: Content safety via `INotificationContentPolicy` per-type allowlist — metadata + links only, never body/payload

- **Decision**: `INotificationContentPolicy` pure domain service `NotificationContent Compose(NotificationType type, IntegrationEvent evt)` that builds `Title` (1..200), `Body` (1..2000) and `Link` (1..500) from an allowlist per type. For `DocumentApprovedIntegrationEvent(documentId, approverId, approvedAt)` it reads only `DocumentId`, `Classification` label (from `Documents.Contracts` event's classification when available via enrichment? spec says integration event carries classification — if `DocumentApprovedIntegrationEvent` currently lacks `Classification`, we enrich at composition from `NotificationDispatcher` context using `evt.DocumentId` already? chosen: composition uses only fields present on the integration event — if classification is missing, title is `Document {DocumentId} approved` without classification label, never fetching document body; classification if available is `Confidential` label only, no body bytes). For `LlmResultGeneratedIntegrationEvent(resultId, operationId, documentId, operationType)` it uses `ResultId`, `OperationType` label, `DocumentId`, never `ProvenanceJson` contents beyond count (title `AI review {OperationType} generated for document {DocumentId}`, body `Result {ResultId} — open to review`, link `/documents/{DocumentId}/ai-results/{ResultId}`). For `WorkItemAssignedIntegrationEvent(workItemId, projectId, tenantId, assigneeId, assignerId)` it uses `WorkItemId`, `ProjectId`, link `/projects/{ProjectId}/work-items/{WorkItemId}`. `Body` never contains `DocumentContent`, `AiResultPayload`, `DocumentVersionContent`. Allowlist is coded per `NotificationType` switch; unknown fields on event are ignored (defense against future `body` field addition — `content-safety regression` edge case fails until switch is extended, but safe default is to ignore). Unit tests `ContentSafetyTests` assert `Body.Contains(documentBody)==false` for `Confidential` and `ProvenanceJson.Length < 1KB` for AI events across all `NotificationType` values.
- **Rationale**: Satisfies R5 + SC-004 0 bytes of document body/AI payload across all templates + Principle XIX (least privilege, no classified data in inbox). Per-type allowlist is stronger than generic allowlist (generic would leak unknown `body` field if event adds one). Link-only for classified docs ensures authorization at navigation time (link target enforces `IDocumentAccessPolicy`), not notification creation time.
- **Alternatives considered**: Generic template `Title = $"{evt.GetType().Name} {evt.ResourceId}"` that reflects all event properties via `JsonSerializer.Serialize(evt)` (rejected — would include `Content`/`Payload` if event adds `byte[] Content`, violates R5). Enrichment that fetches full `Document`/`LlmResult` from producer DB to compose richer body (rejected — would couple BC-09 to producer persistence (violates V) and would expose body that must be masked; composition must be from safe event fields only). Regex masking on `Body` for classified patterns (rejected — too fragile, allowlist is precise).
- **ADR**: `ADR-008-05` records content-safety allowlist per `NotificationType`, never include `DocumentBody`/`AiPayload`/`VersionContent`, and that future event types must extend switch with explicit safe fields.

## Decision 6: CorrelationId propagation via OTel `Activity.Baggage` + `TenantContext` through dispatcher to notification row (observability)

- **Decision**: Middleware `CorrelationIdMiddleware` already in `Api` (`X-Correlation-Id` → `TenantContext.CorrelationId` + `Activity.Current?.SetBaggage("CorrelationId", guid)`). `NotificationsDbContext.SaveChangesAsync` collects `DomainEvent.CorrelationId` from `Activity.Baggage` fallback to `TenantContext.CorrelationId` (same as Audit 007). `NotificationDispatcher.HandleAsync(IntegrationEvent @event)` reads `@event.CorrelationId` if `IntegrationEvent` subtype carries it (for `LlmOperation*` events that already have `CorrelationId` param) else `TenantContext.CorrelationId` from `Activity.Baggage`, and sets `Notification.CorrelationId` on the row. `NotificationCreated` carry `CorrelationId` for `AuditEventConsumer` timeline. Structured logging in dispatcher/channel includes `sourceEventId`, `correlationId`, `notificationType`, `recipientId`, `channel`, `deliveryState` for failure observability (dead-letter visibility per FR-009 via log query, not separate dead-letter queue). `GetOperationTimeline` analog for notifications is not a separate query — timeline is via `Audit` if notifications emit domain events; notification queries themselves filter by `RecipientId` + `CreatedAt`.
- **Rationale**: Satisfies FR-009 channel failures observable via structured telemetry + correlation via OTel + Principle XVIII (every distributed operation traceable). Reuses same propagation chain as 007 audit (no new infra). Keeps notifications queryable by `RecipientId` primary index (no cross-tenant scan).
- **Alternatives considered**: Push `CorrelationId` as explicit `IntegrationEvent` header `EventBus` extension (considered — but per-type `CorrelationId` param on `Llm*` events already exists; for work/document events added later `CorrelationId` can be header `IDictionary<string,string> Headers` on `IntegrationEvent` base if needed; not breaking for MVP). Separate `notification_failures` dead-letter queue (rejected — structured log + `DeliveryState=Failed` row is sufficient observability per FR-009 without new queue; RabbitMQ dead-letter can be enabled later behind `IChannel` without changing dispatcher).
- **ADR**: `ADR-008-06` records propagation reused from 007, `Notification.CorrelationId` nullable for MVP, and that dead-letter visibility is log + `DeliveryState` row (no separate queue).
