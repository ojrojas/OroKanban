# Implementation Plan: Notifications and Collaboration

**Branch**: `008-notifications-collaboration` | **Date**: 2026-09-01 | **Spec**: [spec.md](spec.md) | **Depends on**: 003-projects-work-kanban (WorkItem* integration events, `WorkItemAssigned`), 005-document-management (Document* integration events, classification metadata), 006-llm-document-intelligence (`AiReviewRequested` / `LlmResult*` integration events), 004-metrics-progress-planning (`RiskIncreased`) + 002-identity-access-organization (`TenantContext`, `IManagementHierarchy`) + 007-audit-monitoring-compliance (outbox/consumer patterns)

**Input**: Feature specification — BC-09 Notifications (Supporting). R1 event-driven generation ONLY from integration events (assignments, reassignments, overdue, blocked, completed, review requested, document uploaded/classified/approved, AI review requested, risk increased), R2 channel-decoupled `InApp` (default) + `Email` (future) + extensible `IChannelRouter` with fan-out where failure never blocks others, R3 deduplication/idempotency via `DedupeKey = eventId + recipient` with at-least-once `IIntegrationEventHandler` and persistence unique constraint, R4 per-user `NotificationPreference` (type × channel) within org policy via `INotificationPolicy` merge (policy mandates override), R5 content safety (metadata + links only, no classified document bodies, no AI payloads). Domain: `Notification` (root `NotificationId`, events `NotificationCreated`/`NotificationRead`), `NotificationPreference` (root per User, event `PreferencesUpdated`), VOs `NotificationType`/`Channel`/`DedupeKey`/`DeliveryState`, domain services `INotificationPolicy`/`IChannelRouter`. Application: `NotificationDispatcher` (event→notifications), `EmailChannelConsumer` stub, queries `GetMyNotifications`/`GetUnreadCount`, commands `MarkRead`/`UpdatePreferences`.

## Summary

Implement BC-09 as the supporting bounded context that owns decoupled delivery of attention-requiring changes. Every integration event type from work, documents, AI and risk contexts (11+ types: `WorkItemAssigned`/`Reassigned`/`Overdue`/`Blocked`/`Completed`/`ReviewRequested`/`DocumentUploaded`/`Classified`/`Approved`/`AiReviewRequested`/`RiskIncreased`) is consumed by `NotificationDispatcher` in `Notifications.Infrastructure` via `BuildingBlocks.EventBus.RabbitMQ` topic `notifications.*` / `work.*` / `document.*` / `ai.*` subscriptions with manual ack + exponential retries (at-least-once), resolved to recipients through pure domain service `INotificationPolicy` (assignee/owner/watchers per event), filtered through `NotificationPreference` + org policy merge (`policy-mandated types cannot be suppressed`), deduplicated on `DedupeKey(SourceEventId, RecipientId, Channel)` with persistence `UNIQUE` on `notifications.notifications(SourceEventId, RecipientId, Channel)` and application-level idempotent insert (duplicate-key → already-delivered), composed into safe metadata-only `Notification` aggregate (`Title`/`Body`/`Link` constructed from allowed fields via `INotificationContentPolicy`), persisted in `notifications` schema (`AppDbContextBase` + `EfRepository` + transactional outbox `IOutboxWriter` for `NotificationCreated`/`NotificationRead` domain events), then fanned out via `IChannelRouter` to `InAppChannel` (always, DB-backed inbox) and `EmailChannel` (stub/no-op in v1 but proving fan-out + failure observability per FR-009) where each channel is independently retryable/observable and failure of one never rolls back the other. Queries `GetMyNotifications`/`GetUnreadCount` are authorization-filtered to recipient only (private inbox, no subtree), `MarkRead` is recipient-only idempotent, `UpdatePreferences` validates enumerations via `Validator<T>`; all slices use `ICommand`/`IQuery` + `IEndpoint` + `Result→HTTP` + `Specification<T>` pre-filter and are exercised through `Api` composition (`src/Api` `MapEndpoints`) + `Web` inbox via `minimal-ui-design-system` + `ngrx-signal-store`. No notification logic leaks into producer BCs; producers remain unchanged beyond emitting their existing integration events.

**Performance Goals**: `GetMyNotifications` paginated page 1 size 20 for user with 10k notifications completes <500 ms p95 (composite index `(RecipientId, CreatedAt desc)` + `DeliveryState` filter); `GetUnreadCount` for 10k notifications <500 ms p95 (indexed `COUNT WHERE RecipientId=@id AND ReadAt IS NULL`); `MarkRead` <100 ms p95; `UpdatePreferences` <200 ms p95; dispatcher handles burst of 50 events fan-out to 5 recipients each (250 notifications) without duplicate on 2× redelivery (0% duplicate rate SC-002); end-to-end `IntegrationEvent` publish → notification queryable within 5 s in 95% deliveries under normal load (SC-001); `Email` failure observable within 1 s via structured log + dead-letter metric without blocking `InApp`.

**Constraints**: Principle I: reuse BuildingBlocks canon — no MediatR/MassTransit/AutoMapper; separate UI via `minimal-ui-design-system` + `ngrx-signal-store` mandates; Principle V: BC-09 isolated, producers → consumers only via `BuildingBlocks.EventBus` `IntegrationEvent` (no direct DbContext cross-reference — enforced by Arch test `NotificationsOnlyConsumesEvents`); Principle VI: rules in Domain via `CheckRule`/`IBusinessRule`/`Specification<T>` — `INotificationPolicy`/`INotificationContentPolicy` are pure domain services, `Notification` invariants (`DedupeKey` required, `Title`/`Body` not containing classified payload) enforced by business rules, not controllers; Principle XV: recipient-only authorization — every query filters by `RecipientId==callerId` first (tenant predicate if `TenantId` present; no subtree expansion for inbox — private); Principle XVII: async via outbox + RabbitMQ, handlers idempotent (`UNIQUE(SourceEventId,RecipientId,Channel)` + catch `23505`), manual ack + exponential retries; Principle XIX: content safety metadata-only, no document bodies/AI payloads in `Title`/`Body`, link-only, deny-by-default; validation via `Validator<T>` for `UpdatePreferences` unknown types → 400; `MarkRead` cross-user → 403 generic denial; Constitution traceability Principles XVII/XIX.

**Scale/Scope**: 2 aggregates (`Notification` immutable except `ReadAt`, `NotificationPreference` mutable with `RowVersion`) + 4 Value Objects/Enumerations (`NotificationType` 11+ values extensible, `Channel` `InApp|Email|...` extensible, `DedupeKey` composite, `DeliveryState` 5 values incl. `Skipped*`) + 2 domain services (`INotificationPolicy` recipient + policy merge, `IChannelRouter`/`INotificationChannel` fan-out, `INotificationContentPolicy` content-safety) + 3 `IIntegrationEventHandler` registrations (work/document/AI/risk) funneled to `NotificationDispatcher` + 2 queries + 2 commands (4 vertical slices) + 2 channel implementations (`InAppChannel` real, `EmailChannel` stub future) + `NotificationsDbContext` with 2 tables + outbox; ~25 new files in `Notifications` module; seeded enumerations: `NotificationType` 11, `Channel` 2, `DeliveryState` 5; no new Aspire resources beyond existing `postgres`/`rabbitmq`/`redis` (notifications reuses `postgres` `notifications` schema + `rabbitmq` `integration_events` topic subscription).
