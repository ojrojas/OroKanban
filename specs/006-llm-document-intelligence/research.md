# Research: LLM and Document Intelligence

**Feature**: 006-llm-document-intelligence | **Date**: 2026-09-01 | **Status**: Complete

No `NEEDS CLARIFICATION` remained — all technical choices are informed by `draft/libraries/buildingblocks.md` + constitution Principles X/XI/XV/XVII + `dotnet-ai` skill technology-selection decision tree + existing modules `Documents`/`Organization` + prior specs 002/005.

## Decision 1: LLM abstraction — `Microsoft.Extensions.AI` `IChatClient` (MEAI) with provider behind `AddChatClient` (no domain SDK)

- **Decision**: Every prompt→response operation goes through `Microsoft.Extensions.AI` abstraction `IChatClient` (and `IEmbeddingGenerator` for embeddings) defined in `Microsoft.Extensions.AI` NuGet `9.*`. Domain defines `ILLMProcessor` as a thin wrapper over `IChatClient` (or uses `IChatClient` directly) — domain never references `OpenAI`/`Azure.AI.OpenAI` SDK types. Infrastructure registers a concrete provider via `services.AddChatClient(builder => builder.UseAzureOpenAIChatClient(...))` or `.UseOpenAIChatClient` or `.UseOllamaChatClient` based on `AI:Provider` config (`openai`|`azure`|`ollama`|`inmemory-dev`). Temperature set explicitly per `ChatOptions` (`Temperature=0f` for factual extraction/summarization, higher for creative only if operation type declares), `MaxOutputTokens` capped, retry via `UseChatClient` + `RetryingChatClient` or Polly `maxRetries 3` with exponential backoff, model version pinned (`gpt-4o-2024-08-06` style, `AI:ModelId` in config), token counting via `Microsoft.ML.Tokenizers` client-side before send to enforce budget, secrets via `AI:ApiKey` from env/KeyVault not `appsettings.json`. Domain handlers depend on `ILLMProcessor` (which wraps `IChatClient`) and are tested with `NSubstitute` deterministic stubs (no network).
- **Rationale**: Satisfies R1 + R2 + dotnet-ai decision tree row 2 (Natural language generation → LLM via MEAI) + layer rule "Start with MEAI, add provider SDK behind it" + anti-pattern "Calling OpenAI SDK directly in business logic instead of through MEAI". Keeps domain provider-agnostic and testable, allows swap `openai↔azure↔ollama` via config without domain change, satisfies testability (`IChatClient` fake deterministic). Mirrors MEAI guidance in skill Step 1b abstraction layer.
- **Alternatives considered**: Direct `OpenAI` SDK in Domain (rejected — violates R2, leaks provider, not testable, skill anti-pattern); `Microsoft.SemanticKernel` (rejected — superseded per skill anti-pattern, redirect to MEAI+MAF); raw `HttpClient` to OpenAI (rejected — mixing layers, skill violation `Stack coherence rule`).
- **ADR**: ADR-006-01 records provider selection, model pinning, temperature/retry/token guardrails per dotnet-ai Step 3 LLM guardrails.

## Decision 2: Vector data — `Microsoft.Extensions.VectorData.Abstractions` + provider connector (InMemory dev, Qdrant/PgVector prod)

- **Decision**: `Microsoft.Extensions.VectorData.Abstractions` (`VectorStore`, `VectorStoreCollection<TKey,TRecord>`, `IEmbeddingGenerator`) is the abstraction for embeddings/vector search. Domain defines `IEmbeddingProvider` as `IEmbeddingGenerator<string, Embedding<float>>` + `VectorStore` behind it. Infrastructure adapter: `InMemoryVectorStore` (from `Microsoft.Extensions.VectorData.Abstractions` sample) for dev/tests (zero infra, deterministic, no container), `Qdrant.Client` connector (`QdrantVectorStore`) or `Npgsql.Vector`/`PgVector` for prod (collection per tenant or partition key `tenantId` + filterable payload `classification`, `projectId`, `isSafe`, `isCurrentVersion`). `VectorStore` is tenant-scoped: every `SearchAsync` includes filter `tenantId==ctx.TenantId` and is only reachable via `IAuthorizedRetrievalPolicy` (Architecture test enforces). Embeddings cached in vector store (never re-embed same chunk on every query). Batch embedding via `GenerateAsync(IEnumerable<string>)` where provider supports it. No domain references `Qdrant`/`Npgsql` SDK types.
- **Rationale**: Satisfies R1 row 6 (Semantic search/RAG → VectorData + connector) + row 7 (Ingestion→VectorStore via DataIngestion) + Principle XV (tenant isolation) + R8 global-index forbidden. InMemory for dev keeps Aspire minimal (no Qdrant container required for `dotnet test`), prod connector swappable via config `VectorStore:Provider=qdrant|pgvector`. Provider-agnostic abstraction satisfies testability (InMemory deterministic).
- **Alternatives considered**: Direct `Qdrant.Client` in Domain (rejected — violates R2, skill layer rule); `pgvector` only (rejected — couples to Postgres, harder to swap; abstraction covers both); no VectorData abstraction, custom embedding table (rejected — violates dotnet-ai mandate, loses provider swappability).
- **ADR**: ADR-006-01 records connector choice, tenant-scoped collection vs partitioned index, embedding model (`text-embedding-3-small` pinned) per skill.

## Decision 3: Chunking/Ingestion — `Microsoft.Extensions.AI.DataIngestion` (preview) deterministic 512/50 semantic-aware

- **Decision**: `Microsoft.Extensions.AI.DataIngestion` (`DataIngestion` + `IChunker` or `TextChunker`) for `Chunking` stage, configured deterministic: chunk size 512 tokens (measured via `Microsoft.ML.Tokenizers` tiktoken), overlap 50, semantic-aware split on paragraph/section boundaries before fixed-size fallback. Chunker is deterministic: same content + same params → same `ChunkReference` list (numbered 0..n). Chunks stored as `VectorStoreRecord` with payload `DocumentId`, `DocumentVersionId`, `TenantId`, `Classification`, `ProjectId`, `IsSafe=true`, `IsCurrentVersion` (true for current version, false for superseded), `ChunkId`, `Text`. `Chunking` stage runs after `Classification` and only if `document.IsSafe && status∈{Available,Approved}` — else skips (never indexes unsafe/deleted). `QualityIndicator.chunkCount` reflects split count. Ingestion pipeline `DataIngestion.IngestAsync` + `UpsertAsync` via VectorStore is behind `IEmbeddingProvider`.
- **Rationale**: Satisfies R1 row 7 + R3 pipeline `Chunking→Indexing→Embedding` + R12 `ChunkReference` VO value-equality + edge case large document handling. DataIngestion is the skill-mandated library for chunking/loading (avoids hand-rolled overlapping windows). Deterministic chunking enables idempotent retry (same content → same chunks, no duplicates).
- **Alternatives considered**: Hand-rolled fixed 512 fixed-size chunker (rejected — loses semantic boundaries, violates RAG guardrail "Semantic chunking over fixed-size"); no chunking (rejected — token limit overflow); custom chunk table in PG only (rejected — violates dotnet-ai DataIngestion mandate).
- **ADR**: ADR-006-03 part of chunking strategy (512/50).

## Decision 4: Pipeline orchestration — `LlmOperation` aggregate reusing SPEC-005 outbox job pattern (per-stage map + idempotent RabbitMQ)

- **Decision**: `LlmOperation : AggregateRoot<LlmOperationId>` with fields `DocumentId`, `DocumentVersionId` (snapshot), `OperationType`, `OperationStatus`, `ModelDescriptor`, `PromptVersionId`, `CorrelationId`, `StageStatuses : Dictionary<AiProcessingStage,StageStatus>`, `AttemptCount`, `LastError`, `RowVersion`. Stages: `Extraction(1)→Normalization(2)→Classification(3)→Chunking(4)→Indexing(5)→Embedding(6)→LlmProcessing(7)→Validation(8)→HumanReview(9)` as `Enumeration` (or reuse `ProcessingStage` if shared). Flow: `QueueLlmOperation` handler in one `AiProcessingDbContext` transaction persists `LlmOperation(CurrentStage=Extraction, AttemptCount=0)` + outbox `LlmOperationQueuedIntegrationEvent` with `CorrelationId` (propagated via `TenantContext` → OTel baggage); `OutboxProcessor` publishes to RabbitMQ topic `ai.processing.extraction` etc. Each stage `IIntegrationEventHandler<LlmProcessingStageRequestedIntegrationEvent>` does: load operation with `RowVersion`, set stage `InProgress`, execute domain logic (extraction via IChatClient, chunking via DataIngestion, embedding via IEmbeddingProvider, LLM via IChatClient, validation via IResultValidationPolicy), on success `Succeeded` + advance `CurrentStage` + emit `LlmOperationStageCompleted` + publish next stage event, on failure `FailedRetryable` + increment `AttemptCount` + emit `LlmOperationFailed` + schedule retry exponential backoff `2^attempt*500ms` capped 30s via Polly/`IEventBus` delay. Handlers idempotent: duplicate `EventId` or `(OperationId,Stage,Attempt)` dedup via `outbox_consumed_events` table. `RetryLlmOperation` command resets failed stage to `Pending` and republishes. `maxAttempts=3` per stage → `FailedPermanent` (same as SPEC-005). No LLM call blocks `QueueLlmOperation` HTTP (SC-001 <300ms).
- **Rationale**: Satisfies R3 + FR-004/018/021 + XVII + reusability of SPEC-005 proven `DocumentProcessingJob` pattern (research Decision 4) — keeps consistency across bounded contexts, outbox transactional guarantee, at-least-once + idempotency, OTel correlation. Mirrors metrics pipeline pattern from spec 004 research Decision 5 (proven).
- **Alternatives considered**: In-process BackgroundService without outbox (rejected — loses messages on crash, violates XVII); per-stage HTTP call (rejected — blocks request, no resume); single monolithic handler (rejected — not resumable, failures lose partial progress).
- **ADR**: ADR-006-02 records stage order and retry semantics.

## Decision 5: Review policy — versioned `IReviewPolicy` table default-true (safe) pure domain service

- **Decision**: `IReviewPolicy { bool RequiresReview(OperationType op, string classification, string? policyVersion); }` where `policyVersion` is optional tenant config version. Storage: `ai_processing.review_policies` table (`tenantId`, `operationType` int/enum, `classification` string, `requiresReview` bool, `effectiveFrom` UTC, `isCurrent` bool). Seeded safe defaults via skill guidance: all operations default `true` when no row matches (deny-by-default per Principle XIX) — e.g., `deadlineExtraction × Confidential → true`, only `summarization × Public → false` if explicitly configured (`SC-003` fixtures use this row). Policy service is pure/domain-testable: `RequiresReview` is deterministic `if (!policies.TryGetValue((op,classification), out var row)) return true`. Versioned: `effectiveFrom` + `isCurrent` allows policy evolution without mutating history — results store `ReviewStatus` snapshot at generation time (not re-evaluated on read). `LlmResult` constructor calls `RequiresReview` to decide `Generated` vs `PendingReview` initial status.
- **Rationale**: Satisfies R7 + FR-010 + Principle XI configurable per operation×classification×policy + safe default `true` when misconfigured (edge case). Pure service enables `ReviewPolicyMatrixTests` (12 operation types × 5 classifications) without DB. Mirrors `IClassificationPolicy` versioning in SPEC-005 for consistency.
- **Alternatives considered**: Hard-coded switch per operation (rejected — violates R7 configurable, Principle VI); unversioned bool in config (rejected — loses auditability, cannot answer "why was this result PendingReview?"); always `true` (rejected — burdens Public summarization).
- **ADR**: ADR-006-04 records policy table vs simple config decision (table chosen for auditability + versioning).

## Decision 6: Provenance — mandatory `Provenance` VO validated at `LlmResult` construction (no null)

- **Decision**: `Provenance : ValueObject` with components `SourceDocumentId (Guid)`, `SourceDocumentVersionId (Guid)`, `OperationId (Guid)`, `OperationType (int/string)`, `Model (ModelDescriptor VO)`, `PromptVersion (string/id)`, `CreatedAt (DateTime UTC)`, `CreatedBy (Guid/System)`, `ProcessingStatus (string)`, `QualityIndicator (VO?)`. `LlmResult` constructor takes `Provenance provenance` required param and calls `CheckRule(new ProvenanceCompleteRule(provenance))` which validates all required fields non-default/non-empty; if broken returns `Error.Validation("Provenance.Required")` and no row is persisted (FR-006). Snapshot: provenance is copied at generation time (operation `Model` + `PromptVersion` + `CreatedBy` snapshotted, not live reference per R6/R5). Equality is `GetEqualityComponents()` over all fields (allows provenance completeness unit test via value equality). `ModelDescriptor` is VO `Provider (string)`, `ModelName (string)`, `Version (string)` pinned per skill. `QualityIndicator` is VO `Confidence (float? 0..1)`, `QualityScore (float?)`, `IsInjectionFlagged (bool)`, `ChunkCount (int?)`, `TokenCount (int?)`. No result row where `provenance IS NULL` — DB column `provenance_json` is `NOT NULL jsonb`.
- **Rationale**: Satisfies R5 + FR-006/007 + Principle X — every result traceable, audit can field-by-field assert. Mirrors `MetadataSnapshot` VO in SPEC-005 but for AI lineage. Prevents "result without provenance" compliance violation at domain layer (not just DB constraint).
- **Alternatives considered**: Nullable provenance with DB `NULL` allowed (rejected — violates R5 "No AI result exists without provenance"); separate `provenance` table (rejected — over-normalized, snapshot semantics require jsonb copy).

## Decision 7: Prompt versioning — append-only `LlmPromptVersion` with `PromptIsImmutableOncePublishedRule`

- **Decision**: `LlmPromptVersion : AggregateRoot<LlmPromptVersionId>` per FR-005, fields `OperationType`, `VersionNumber (int 1..n monotonic per operation type, UNIQUE (OperationType, VersionNumber))`, `Template (string 1..20k, must contain {{content}} placeholder)`, `IsPublished (bool true after publish)`, `PublishedAt/By`, `RowVersion`. `PublishPromptVersion` command always inserts new row: `version = maxVersion(OperationType)+1`; `PromptVersionPublished` emitted. `IsPublished=true` → private setters throw `PromptIsImmutableOncePublishedRule` via `CheckRule` (verified by reload equality test SC-002). `LlmOperation` and `LlmResult` store `PromptVersionId` snapshot (not FK live) — historical fidelity per R6. Operation without explicit `PromptVersionId` resolves to `MAX(VersionNumber) WHERE IsPublished` at queue time (current version snapshot).
- **Rationale**: Satisfies R6 + FR-005/019 + Principle X prompt lineage — mirrors SPEC-005 `DocumentVersion` append-only but per operation type. Provides reproducible audit ("why did summarization produce this output?").
- **Alternatives considered**: In-place template update (rejected — violates R6 immutability, breaks SC-002); event-sourcing for prompts (rejected — over-engineering, EF append rows suffice).
- **ADR**: ADR-006-02 variant for prompt lifecycle.

## Decision 8: Authorized retrieval — pure `IAuthorizedRetrievalPolicy` as Golden Rule B pre-filter before vector ranking

- **Decision**: `IAuthorizedRetrievalPolicy { Task<IReadOnlyList<ChunkReference>> FilteredSearchAsync(Embedding<float> queryEmbedding, AccessContext ctx, int topK, float minScore, CancellationToken ct); }` pure domain (no I/O except injected `IDocumentAccessPolicy` + `IManagementHierarchy`/`IProjectMembership` reads + VectorStore filtered search). Logic: (a) embed query via `IEmbeddingProvider` (outside policy, but embedding does not leak content); (b) compose filter spec: `tenantId == ctx.TenantId && classificationLevel <= actorMaxLevel && (isSafe==true && status∈{Available,Approved} && isCurrentVersion==true) && (ownerId==actorId || explicitGrant || IManagementHierarchy.IsInSubtree || IProjectMembership.IsMember)` as chunk metadata predicate; (c) call `VectorStore.SearchAsync(queryEmbedding, new VectorSearchOptions { Top=topK, Filter=metadataFilter, MinimumScore=minScore })` where provider supports server-side filter (Qdrant/PgVector); for InMemory fall back to LINQ pre-filter before similarity ranking. Only authorized `ChunkReference`s are ranked; global scan without filter is never called (Architecture test asserts no `VectorStore.SearchAsync` outside policy class). Policy is deny-by-default, OR over grants (same as `IDocumentAccessPolicy` in SPEC-005). Chunk metadata always includes `tenantId`, `classification`, `projectId`, `isSafe` for filtering — verified at chunk indexing time via `IResultValidationPolicy`.
- **Rationale**: Satisfies R8 + FR-011 + Golden Rule B ("input side") + Principle XV/XIX deny-by-default + SC-004/005 leakage 0. Pre-filter before ranking is critical: post-filter ranking leaks similarity scores of unauthorized chunks and allows embedding-based inference. Pure testable via fakes to exhaust SPEC-013 matrix (5 classifications × N actor types × 2 branches). Mirrors `IDocumentAccessPolicy` OR semantics from SPEC-005 for consistency.
- **Alternatives considered**: Post-filter after ranking (rejected — leaks scores, skill RAG guardrail "filter before ranking" violation); separate per-chunk ACL table (rejected — cross-module join complexity; metadata on chunk suffices); client-side filtering after VectorStore returns all (rejected — requires global read, violates "global indexes are forbidden").
- **ADR**: ADR-006-03 records pre-filter vs post-filter choice (pre-filter chosen).

## Decision 9: Prompt-injection hardening — structured `{{content}}` data boundary + `IResultValidationPolicy` heuristic

- **Decision**: Prompt templates MUST contain `{{content}}` placeholder; at render time document `content` (untrusted) is injected as a `User` role message chunk with explicit boundary (e.g., `ChatMessage` role `User` with text `"<document_content>\n{content}\n</document_content>"` or via `ChatOptions` tool `Content` part tagged `data`), never concatenated into `System` instruction. `IResultValidationPolicy { (bool isFlagged, string sanitized) Validate(string rawContent, string llmOutput); }` scans raw content for injection markers (regex for `Ignore previous instructions`, `SYSTEM:`, `### Instruction`, etc.) and scans `llmOutput` for obedience to injected instruction (heuristic + comparison to expected schema); sets `QualityIndicator.IsInjectionFlagged=true` when flagged and sanitizes output (strips injected directive). `ChatOptions.Temperature=0` for factual tasks reduces hallucination of following injection. Regression suite `PromptInjectionRegressionTests` seeds doc `D_C` with injection payload and asserts `IsInjectionFlagged` and output does not contain "secrets revealed" per spec.
- **Rationale**: Satisfies FR-016 + Principle XIX + security acceptance criterion prompt-injection regression (US5). Structured boundary keeps untrusted data as data (ChatMessage role separation is MEAI semantic). Validation policy is pure/domain-testable with deterministic heuristic (no LLM call in test).
- **Alternatives considered**: No boundary (template string replace into instruction) (rejected — injection succeeds); LLM-based injection detector (rejected — non-deterministic, cost, violates "do not use LLM for deterministic task" per skill); no validation (rejected — violates R8 security hardening).
- **ADR**: ADR-006-03 includes injection boundary.

## Decision 10: No ML.NET branch (LLM-only for this spec)

- **Decision**: For this feature, no structured/tabular ML task is identified — all 12 operation types are NLP over unstructured document text (summarization, extraction, etc.) which the decision tree maps to LLM via MEAI, not ML.NET. Explicitly document `No ML.NET` in Technical Context; if a future deterministic subtask (e.g., numeric risk scoring from structured fields) is identified, it will be a hybrid: `ML.NET` for scoring + LLM for explanation via separate slice, justified via ADR.
- **Rationale**: Satisfies dotnet-ai critical rule "Do NOT use an LLM for tasks ML.NET handles well" — we did not use LLM for tabular, but there is no tabular task here, so LLM is correct. Avoids mixing abstractions. Documented to prevent future LLM-over-ML anti-pattern.
- **Alternatives considered**: Use ML.NET for classification operation (rejected — operation is document content classification, not tabular, and skill maps NLP classification to LLM; ML.NET would require feature engineering on text).
