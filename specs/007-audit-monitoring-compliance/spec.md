# Feature Specification: Audit, Monitoring and Compliance

**Feature Branch**: `007-audit-monitoring-compliance`

**Created**: 2026-09-01

**Status**: Draft

**Input**: User description: "SPEC-007 — Audit, Monitoring and Compliance **Bounded Context**: BC-08 Audit (Supporting) + platform monitoring · **Depends on**: SPEC-001 (all contexts emit events) ## Objective Provide complete, append-only accountability for security and business actions, plus operational monitoring (Constitution Principle VIII, XVIII). ## Requirements **R1 — Append-only audit store**: `AuditEntry` records: `AuditId`, `Timestamp`, `Actor`, `Action`, `ResourceType`, `ResourceId`, `Organization/Tenant`, `Result`, `CorrelationId`, client metadata (where permitted), and before/after snapshots (sensitive fields masked). Entries are never updated or deleted; corrections are new entries. Tamper-evidence (e.g., hash chaining) SHOULD be evaluated in an ADR. **R2 — Event catalog (minimum)**: authentication outcomes; authorization denials; project/work-item creation and modification; assignment/status/metric changes; document lifecycle (upload, classify, version, access, denial, delete, approve); permission and grant changes; hierarchy changes; AI operations, results, and review decisions; configuration changes. **R3 — Emission path**: Audit events flow domain events → outbox → integration events → audit consumer (idempotent). Correlation IDs from OTel propagation are embedded. **R4 — Audit search**: Authorized managers/auditors filter by actor, action, resource, project, organization, date range, result, correlation ID — authorization-filtered by the same Golden Rule A (an auditor sees what their scope permits). **R5 — Operational dashboards**: Service health, failed requests, background jobs (document processing, AI ops), queue depth, latency, DB errors, authorization failures — surfaced via Aspire dashboard + OTel backends (alerts via ADR)."

**Bounded Context**: BC-08 Audit (Supporting) + platform monitoring — Depends on SPEC-001 (all bounded contexts emit domain→outbox→integration events); horizontal capability that consumes but never produces domain state for other BCs.

**Constitution Traceability**: Principles VIII (Everything Important Is Auditable — append-only, tamper-evident), XVIII (Observability Mandatory — OTel/Serilog/health), XV (Tenant/Organization Aware), VII (Hierarchical Authorization — Golden Rule A), VI (Domain Rules in Domain), XXI (TDD+DDD+Vertical Slices), XXII (Skills Govern — minimal-ui-design-system for dashboards); §Architecture Final Rule (Explicitness over Magic); §Governance (Compliance Review).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Append-only audit trail for every catalogued action (Priority: P1)

As a compliance officer, I want every action in the R2 catalog (authentication, authorization denial, project/work-item changes, document lifecycle, grants, hierarchy, AI ops, config) to create an immutable `AuditEntry` with actor, resource, result, timestamp, and correlation ID, so that no security or business event goes unrecorded and the trail is tamper-evident.

**Why this priority**: Directly implements Principle VIII and R1/R2/R3 — without it the platform cannot prove what happened, who did it, or under which distributed transaction. All other audit/monitoring stories depend on the store existing. P1 because missing audit is a compliance blocker.

**Independent Test**: Can be fully tested by performing one action from each R2 category as distinct actors (e.g., failed login, denied `GetDocument`, created project, moved work item, uploaded document, denied access, approved AI result) with a common `CorrelationId` propagated via OTel — then querying `SearchAuditEntries` as an auditor scoped to those resources — and verifying one `AuditEntry` per action exists with non-null `AuditId`, `Timestamp` within tolerance, `Actor` == performer, `ResourceType/ResourceId` match target, `Result` (Success/Denied/Failed), `CorrelationId` equals propagated value, and masked `BeforeAfterSnapshot` never leaks sensitive fields. Re-delivering the same integration event (duplicate) creates zero additional entries (idempotency).

**Acceptance Scenarios**:

1. **Given** an authentication outcome (success or failure) with `CorrelationId = C1`, **When** the authentication domain event is emitted via outbox, **Then** an `AuditEntry` appears with `Action = AuthenticationSucceeded|AuthenticationFailed`, `Actor` = attempted identity (or `System` for token expiry), `ResourceType = Authentication`, `Result` = `Success|Failed`, `CorrelationId = C1`, `Timestamp` ≈ event time, and `ClientMetadata` (IP, user-agent where permitted).
2. **Given** any R2 action (e.g., `DocumentApproved` by `ApproverId = A` on `DocumentId = D`), **When** the corresponding domain event `DocumentApproved` completes its outbox→integration→audit consumer journey, **Then** an `AuditEntry` exists with `Action = DocumentApproved`, `Actor = A`, `ResourceType = Document`, `ResourceId = D`, `Organization/Tenant = T`, `Result = Success`, `BeforeAfterSnapshot` containing `Before: status=PendingApproval → After: status=Approved` with `ContentHash` preserved but `ApiKey`/`Secret` fields masked as `***`, and the entry is queryable within 2 seconds of commit.
3. **Given** duplicate delivery of the same integration event (same `EventId`), **When** the `AuditEventConsumer` handles it a second time, **Then** no second `AuditEntry` is created — consumer keys on `(EventId)` or `(ResourceType, ResourceId, AuditAction, CorrelationId)` dedup and returns success without side effect.

### User Story 2 - Immutability and tamper-evidence (Priority: P1)

As a platform owner, I want `AuditEntry` to be immutable by design — no update or delete path exists in the domain or persistence — and tamper-evidence to be evaluable, so that an attempt to alter history is structurally impossible and detectable.

**Why this priority**: Extends US1 with the second acceptance criterion (no mutators compiled) and R1 corrections-as-new-entries. Without immutability, audit is not trustworthy. P1 alongside US1; without it, entries could be erased.

**Independent Test**: Can be fully tested by loading a persisted `AuditEntry` via repository and attempting every mutation vector: domain `AuditEntry` exposes no setters (only constructor/init), repository exposes only `AddAsync` (no `Update`/`Remove`), `DbContext` `AuditEntries` `DbSet` is configured with `IsImmutable` simulation (no `SaveChanges` update tracking) — attempts to change `Action` and call `SaveChanges` throw or are ignored and reload shows original value. A direct SQL `UPDATE audit_entries SET action='Tampered'` either fails due to DB `REVOKE UPDATE, DELETE` for app role or is detectable via hash-chain validation (`PreviousHash` mismatch) if hash chaining is implemented per ADR.

**Acceptance Scenarios**:

1. **Given** a persisted `AuditEntry` `E1` with `Action = DocumentUploaded`, **When** code attempts `E1.Action = "Tampered"` or `repository.Update(E1)` or `dbContext.AuditEntries.Update(E1)`, **Then** compilation fails (no setter/method) or runtime throws `NotSupportedException`/`InvalidOperationException` and a reload `GetAuditTrail(resourceId=D)` still returns the original `Action` unchanged.
2. **Given** a correction is needed for a prior entry (e.g., wrong `Result`), **When** the correction is recorded, **Then** a *new* `AuditEntry` with `Action = AuditCorrected`, `ResourceId = E1.AuditId`, `BeforeAfterSnapshot = { Before: E1.Result, After: CorrectedResult }`, and incremented `SequenceNumber`/`HashChain` is appended — `E1` remains untouched and timeline shows both entries ordered by `Timestamp`.
3. **Given** hash chaining is adopted per ADR (evaluated during planning), **When** entries are chained as `Entry.Hash = SHA256(PreviousHash || AuditId || Timestamp || Action || Actor)`, **Then** verification `VerifyChain()` recomputes hashes and detects any tampered row (mismatch returns `Error.DataCorrupted`) and an integration test asserts tamper detection within the test suite.

### User Story 3 - Authorization-filtered audit search and per-resource trails (Priority: P1)

As an authorized manager/auditor, I want to search audit entries by actor, action, resource, project, organization, date range, result, correlation ID — and retrieve per-resource trails and per-correlation timelines — with results filtered by the same Golden Rule A so I only see entries within my hierarchical scope, so that audit search respects least-privilege and branch isolation.

**Why this priority**: Implements R4 and the third acceptance criterion (cross-branch filtered out) — without it an auditor in branch A could read branch B's compliance data, violating Principle XV/VII. P1 because unfiltered audit is a data leak.

**Independent Test**: Can be fully tested by seeding `AuditEntry` rows for two branches under same tenant with disjoint subtrees: Branch A (manager Alice owns project P_A) with entries `E_A1, E_A2` (actions `ProjectCreated`, `DocumentAccessDenied` on P_A), Branch B with `E_B1` on P_B; as Alice (scoped to subtree A + project P_A), `SearchAuditEntries(filters: actor=Alice, dateRange=last 7d)` returns only `E_A1, E_A2` (zero `E_B1`), `GetAuditTrail(resourceId=P_B)` returns 404/empty (not 403 enumeration), `GetOperationTimeline(correlationId=C_B_for_B_branch)` for B's workflow returns 404; as super-auditor with tenant-wide scope, all three are visible. Filter combinations (actor+action+resource+project+org+date+result+correlationId) are individually asserted.

**Acceptance Scenarios**:

1. **Given** an auditor `Auditor_A` whose `IManagementHierarchy` scope is subtree rooted at `OrgUnit_A` (and `ProjectMembership` includes `P_A` only), **When** they call `SearchAuditEntries(filters: projectId=P_A, organizationId=Org_A, actor=Any, dateRange=2026-08-25..2026-09-01)`, **Then** results are `WHERE audit.OrganizationId IN subtree(Auditor_A) AND audit.TenantId==ctx.TenantId AND (audit.ProjectId==P_A OR audit.ResourceId IN resourcesOwnedBySubtree)` paginated, ordered by `Timestamp` desc, and entries for `P_B` (outside subtree) are absent — verified by `CrossBranchAuditSearchTests` (5 actor types × 2 branches).
2. **Given** a `CorrelationId = C1` that spans a distributed document workflow (`HTTP POST /api/documents` → `DocumentUploaded` → storage `DocumentProcessingStageCompleted` → indexing → `LlmOperationQueued` → `LlmResultGenerated` → `LlmReviewCreated`), **When** any authorized participant calls `GetOperationTimeline(correlationId=C1)`, **Then** the timeline returns those audit entries in `Timestamp` order with `Actor`, `Action`, `ResourceType/ResourceId`, `Result`, `BeforeAfterSnapshot` (masked), reconstructing the full workflow — verified by end-to-end `CorrelationPropagationTests`.
3. **Given** an unauthenticated or unauthorized caller (no `auditor`/`manager` role and not owner of resource), **When** they call `SearchAuditEntries` or `GetAuditTrail(resourceId)`, **Then** result is `Error.Forbidden` (or 404 shadow for resource-level to avoid enumeration) and no entries leak — and the *attempt* itself is audited as `AuditSearchDenied`.

### User Story 4 - Operational monitoring and health dashboards via Aspire + OTel (Priority: P2)

As an operator/SRE, I want operational health — service health per dependency, failed request rate, background job state (document processing, AI ops), queue depth, latency, DB errors, authorization failures — surfaced via Aspire dashboard and OTel backends with identifiable per-dependency failures, so that a critical outage is immediately diagnosable.

**Why this priority**: Implements R5 and the fifth acceptance criterion (critical dependency outage identifiable). P2 after audit correctness P1 stories because monitoring is supporting but not compliance-blocking; still required for production operability.

**Independent Test**: Can be fully tested by with `Aspire` `AddServiceDefaults()` OTel flow running: `GET /health` returns `Healthy` when postgres/rabbitmq/redis/AI provider are reachable; simulating outage (stop postgres container or stub `IChatClient` to throw `ProviderUnavailable`) makes `/health`→`Unhealthy` with `HealthReport.Entries["postgres"]` or `Entries["ai_provider"]` status `Unhealthy` and `Metrics` `http_requests_failed` increments; `GET /alive` remains `Healthy` (liveness vs readiness split). Dashboard shows `QueueDepth` gauge for `document_processing` and `ai_processing` topics, `Latency` histogram for `QueueLlmOperation` <300ms p95, `AuthorizationFailure` counter increments on 403, and logs correlate via `CorrelationId` baggage (`traceId`).

**Acceptance Scenarios**:

1. **Given** all dependencies healthy (`postgres`, `rabbitmq`, `redis`, `ai_provider` stub healthy), **When** `GET /health` (readiness) is called, **Then** it returns `200 Healthy` with `Entries: { postgres: Healthy, rabbitmq: Healthy, redis: Healthy, ai_provider: Healthy, vector_store: Healthy }` and OTel `health_check` metric is `1`.
2. **Given** postgres is down (or `Npgsql` throws `SocketException`), **When** `GET /health` is called, **Then** it returns `503 Unhealthy` with `Entries["postgres"] = Unhealthy` and `Description` contains `Npgsql` error without leaking `ConnectionString` (`***` masked), and the failure is distinguishable from `rabbitmq` failure (`Entries["rabbitmq"]` still `Healthy`) — verified by `HealthPerDependencyTests`.
3. **Given** a background job (`DocumentProcessingJob` or `LlmOperation`) in `FailedRetryable` after `maxAttempts`, **When** dashboard metrics are scraped, **Then** `job_failed_total{job="document_processing", stage="VirusScan"}` increments and appears in Aspire dashboard `Metrics` and OTel `Counter` with `TenantId` tag (no PII), and queue depth `rabbitmq_queue_depth{queue="ai.processing.embedding"}` is observable.
4. **Given** a period of 100 requests with 5 failed (4 authorization `403` + 1 DB `500`), **When** metrics are queried, **Then** `http_requests_failed_total{status="403"}` = 4 and `http_requests_failed_total{status="500"}` = 1, latency histogram `http_request_duration_ms{endpoint="QueueLlmOperation"}` p95 <300ms is recordable, and authorization failures are also appended as `AuditEntry` with `Action=AuthorizationDenied` (dual observability: metrics + audit).

### Edge Cases

- What happens when the audit consumer receives the same integration event twice (at-least-once delivery)? Consumer keys on `(EventId)` dedup via `audit_consumed_events(EventId)` or `(ResourceType,ResourceId,AuditAction,CorrelationId)` — second delivery returns success with no second `AuditEntry`; integration test `ConsumerIdempotencyTests` asserts count == 1 after duplicate.
- What happens when an auditor queries a date range that spans no entries or is inverted (`from > to`)? `SearchAuditEntries` returns empty `PagedResult` with `totalCount=0` (not 400) for no entries; inverted range returns `Error.Validation("Audit.DateRangeInvalid")`.
- What happens when `BeforeAfterSnapshot` contains sensitive fields (`ApiKey`, `Password`, `Secret`, `ConnectionString`)? `IAuditMaskingPolicy` replaces values with `***` before persistence; unit `MaskingPolicyTests` asserts `Snapshot["ApiKey"] == "***"` and raw value never reaches `AuditEntry`.
- What happens when `CorrelationId` is missing from incoming HTTP (no OTel baggage)? Middleware generates `CorrelationId = Guid.NewGuid()` at request entry, propagates via `AsyncLocal` + `Activity.Baggage` + `TenantContext`, and embeds in the resulting `AuditEntry`; timeline still reconstructible via generated ID.
- What happens when tenant header is missing or cross-tenant access is attempted? All audit commands/queries require `TenantContext`; cross-tenant `SearchAuditEntries` with `tenant_id=T2` for resource in `T1` returns 404 shadow (not 403) to avoid enumeration, per Principle XV.
- What happens when `AuditEntry` volume is high (1k entries for same resource, or 10k tenant-wide)? `SearchAuditEntries` is paginated (`page/pageSize` 1..100, default 50) and `GetAuditTrail` caps at 500 with `Link` header for next page; performance goal <300ms p95 for 1k entries paginated (indexed `Timestamp` desc + `TenantId`).
- What happens when a background job (document processing, AI op) emits no explicit domain event (e.g., `VirusScan` stage failure is only `DocumentProcessingFailed`)? `AuditEventConsumer` still produces an `AuditEntry` for every `*Failed`/`*StageCompleted` integration event — the catalog includes job stage completions/failures as auditable `Action`s (`DocumentProcessingFailed`, `AiStageFailed`).
- What happens when an action targets multiple resources (e.g., `ProjectMemberAdded` affects project and user)? The consumer emits one `AuditEntry` per resource perspective (primary `ResourceType=Project`, `ResourceId=projectId`, `DetailJson` contains `MemberUserId`) — or two entries if ADR chooses to emit per-resource — documented in `IAuditMaskingPolicy` handling of `ResourceReference` list.
- What happens when OTel backends (Seq/Loki/OTLP) are unavailable? Audit persistence (PG `audit_entries`) still succeeds (audit is not best-effort — it is transactional via outbox); OTel export is best-effort with `BatchActivityExportProcessor` retry — audit trail remains queryable via `SearchAuditEntries` even if traces/metrics are delayed.
- What happens when an auditor lacks `manager` or `auditor` role but is resource owner (e.g., document owner queries own document trail)? `IAuditQueryAuthorization` grants access (OR over owner, subtree manager, `auditor` role, explicit grant) — owner sees own resource trail even without global auditor role, consistent with Golden Rule A.
- What happens when hash chaining is enabled and a new entry must reference `PreviousHash` but the previous entry is concurrently inserted? `PreviousHash` is computed as `SHA256(PreviousEntry.Hash)` within the same DB transaction with `SELECT ... FOR UPDATE` on the tail entry (`audit_entries` tail lock) — concurrent writers serialize on the hash chain lock; insert order is `Timestamp`-ordered, not `AuditId`-ordered.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide `AuditEntry` as `AggregateRoot<AuditEntryId>` (`StronglyTypedId<Guid>`) but conceptually immutable (no update/delete behavior): fields `AuditId`, `Timestamp` (UTC, required), `Actor` (`ActorReference` VO: `ActorId` Guid, `ActorType` `User|System|Anonymous`, `DisplayName` masked), `Action` (`AuditAction` Enumeration, required), `ResourceType` (`string` 1..100, e.g., `Project`, `WorkItem`, `Document`, `DocumentVersion`, `LlmOperation`), `ResourceId` (string/Guid 1..200), `OrganizationId`/`TenantId` (Guid, required), `Result` (`AuditResult` VO: `Success|Denied|Failed` + `ErrorCode` optional), `CorrelationId` (Guid, required, from OTel `Activity.Baggage`), `ClientMetadata` (`IpAddress` 1..45, `UserAgent` max 500, where permitted), `BeforeAfterSnapshot` (VO with `BeforeJson`/`AfterJson` masked — sensitive fields `***`), `PreviousHash` (string? 64 hex if hash chaining enabled, else null). Entries MUST be append-only; the domain exposes no `Update`/`Delete` mutators and `IRepository<AuditEntry>` exposes only `AddAsync` (no `Update`/`Remove`), enforced by architecture test `AuditEntryIsImmutable`.
- **FR-002**: `AuditAction` MUST be an `Enumeration` covering at minimum the R2 catalog: `AuthenticationSucceeded(1)`, `AuthenticationFailed(2)`, `AuthorizationDenied(3)`, `ProjectCreated(4)`, `ProjectUpdated(5)`, `WorkItemCreated(6)`, `WorkItemUpdated(7)`, `WorkItemAssigned(8)`, `WorkItemStatusChanged(9)`, `ProjectMetricChanged(10)`, `DocumentUploaded(11)`, `DocumentClassified(12)`, `DocumentVersionPublished(13)`, `DocumentAccessed(14)`, `DocumentAccessDenied(15)`, `DocumentDeleted(16)`, `DocumentApproved(17)`, `PermissionChanged(18)`, `GrantAdded(19)`, `GrantRevoked(20)`, `HierarchyChanged(21)`, `LlmOperationQueued(22)`, `LlmOperationCompleted(23)`, `LlmOperationFailed(24)`, `LlmResultGenerated(25)`, `LlmResultApproved(26)`, `LlmResultRejected(27)`, `LlmReviewCreated(28)`, `RagQueryExecuted(29)`, `ConfigurationChanged(30)`, `AuditCorrected(31)` — each `AuditAction` maps 1:1 to at least one domain event per ADR.
- **FR-003**: System MUST emit audit via the path domain events → `IOutboxWriter` (transactional, same DB tx as business write) → `OutboxProcessor` polls `SELECT ... FOR UPDATE SKIP LOCKED` → `IEventBus` (RabbitMQ topic `audit.*` + `integration_events`) → `AuditEventConsumer` (background `IHostedService`/`IIntegrationEventHandler`, idempotent) → `AuditEntry` appended; `CorrelationId` from `Activity.Current.Baggage` or `TenantContext.CorrelationId` is embedded in every `AuditEntry`; duplicate `EventId` delivery MUST produce exactly one `AuditEntry` (idempotency via `audit_consumed_events(EventId)` unique or `(ResourceType,ResourceId,Action,CorrelationId)` dedup).
- **FR-004**: `BeforeAfterSnapshot` MUST be a `ValueObject` with `BeforeJson`/`AfterJson` (jsonb, 1..50k) where `IAuditMaskingPolicy.Mask(snapshot)` replaces sensitive keys (`ApiKey`, `Password`, `Secret`, `ConnectionString`, `Token`, `CreditCard`) with `***` before persistence; policy is pure/domain-testable and configurable per `ResourceType` (e.g., `Document` masks `ContentHash`? no — only secrets). Raw unmasked values MUST never reach `audit_entries` table — verified by unit `MaskingPolicyTests`.
- **FR-005**: System MUST expose query `SearchAuditEntries` (`IQuery<Result<Paged<AuditEntryResponse>>>`) with filters `ActorId?`, `Action?` (`AuditAction`), `ResourceType?`, `ResourceId?`, `ProjectId?`, `OrganizationId?`, `TenantId` (required, from `TenantContext`), `DateRange` (`From`/`To` UTC), `Result?`, `CorrelationId?`, `page`/`pageSize` (1..100) — all filters optional except `TenantId`; results ordered by `Timestamp` desc, paginated, never leaking domain entities (DTOs only). Query MUST be authorization-filtered via `IAuditQueryAuthorization` composing Golden Rule A (tenant + subtree via `IManagementHierarchy` + project membership via `IProjectMembership` + explicit grants + role `auditor|manager`) BEFORE fetch — same filter as `IDocumentAccessPolicy` but scoped to audit `OrganizationId`/`ProjectId`.
- **FR-006**: System MUST expose `GetAuditTrail(resourceId)` (`IQuery<Result<Paged<AuditEntryResponse>>>`) returning chronological `AuditEntry` rows for a single resource (`ResourceType+ResourceId`) ordered `Timestamp` asc, authorization-filtered (caller must be able to read the resource per Golden Rule A or be auditor for its tenant/branch) — cross-branch resource for non-scoped auditor returns 404 shadow.
- **FR-007**: System MUST expose `GetOperationTimeline(correlationId)` (`IQuery<Result<IReadOnlyList<AuditEntryResponse>>>`) returning all `AuditEntry` rows sharing `CorrelationId` ordered `Timestamp` asc across resource types, enabling full distributed workflow reconstruction (`HTTP → storage → processing → indexing → LLM → review`) — verified by `CorrelationPropagationTests` end-to-end.
- **FR-008**: System MUST implement `IAuditQueryAuthorization` as pure domain service: `CanActorQuery(actorId, tenantId, filters) → bool` and `BuildAuthorizedFilter(actorId, tenantId) → Expression<Func<AuditEntry, bool>>` that composes `TenantId` predicate + `IManagementHierarchy.IsInSubtree`-derived `OrganizationId` set + `IProjectMembership` projectIds + explicit grants — deny-by-default, OR over grants, value-equality comparable.
- **FR-009**: `AuditEntry` ordering MUST be `Timestamp` desc for search and `Timestamp` asc for trail/timeline (indexed `Timestamp` desc + `TenantId` composite); performance goals: `SearchAuditEntries` 1k entries <300ms paginated, `GetAuditTrail` for single resource 1k <300ms paginated (via `EXPLAIN ANALYZE` verified index `audit_entries_tenant_timestamp_idx` + `audit_entries_resource_idx`).
- **FR-010**: Operational dashboards MUST surface via `AddServiceDefaults()` OTel flow: `GET /health` (readiness, dependency checks via `AddHealthChecks` for `postgres`, `rabbitmq`, `redis`, `ai_provider`, `vector_store`), `GET /alive` (liveness, `HealthCheckResult.Healthy` without dependency checks), Prometheus `Metrics` (`http_requests_total`, `http_requests_failed_total{status, endpoint}`, `job_failed_total{job, stage}`, `rabbitmq_queue_depth`, `http_request_duration_ms` histogram), and structured logs via `Serilog` + OTLP; Aspire dashboard shows service health + Metrics; alerts via ADR (e.g., `Prometheus` `AlertManager` + `Grafana` or OTel `alerts` topic) — this spec only emits metrics/health, not the alerting infrastructure itself.
- **FR-011**: Health checks MUST be per-dependency identifiable per acceptance criterion: `HealthReport.Entries["postgres"]` `Unhealthy` when `Npgsql` `SocketException`, `Entries["rabbitmq"]` `Unhealthy` when `RabbitMQ.Client` `BrokerUnreachableException`, `Entries["redis"]` `Unhealthy` when `StackExchangeRedis` `RedisConnectionException`, `Entries["ai_provider"]` `Unhealthy` when `IChatClient` throws `ProviderUnavailable` — each entry's `Exception.Message` is `***`-masked for secrets but distinct per dependency (architecture test asserts 4 separate `IHealthCheck` registrations).
- **FR-012**: Every business-significant handler MUST propagate `CorrelationId` via `Activity.Baggage` + `AsyncLocal<TenantContext.CorrelationId>` + `IOutboxWriter.CorrelationId` so that `AuditEntry.CorrelationId` equals the originating HTTP `X-Correlation-Id` (or generated `Guid.NewGuid()` at middleware entry if header absent) — verified by `CorrelationPropagationTests` (`HTTP header → TenantContext → Activity → DomainEvent → IntegrationEvent → AuditEntry` chain asserts equality).
- **FR-013**: `ActorReference` MUST be a `ValueObject` (`ActorId` Guid, `ActorType` `User|System|Anonymous`, `DisplayName` 1..200 masked if needed); `ResourceReference` VO (`ResourceType` 1..100, `ResourceId` string) — both value-equality and stored as `jsonb` or columns in `audit_entries`; `AuditResult` VO (`Result` `Success|Denied|Failed`, `ErrorCode` 1..100 optional) — value-equality.
- **FR-014**: Tamper-evidence SHOULD be evaluated per ADR (R1 SHOULD): Decision `HashChaining` vs `NoChaining` with `SHA256(PreviousHash || AuditId || Timestamp || Action || Actor)` chaining and `PreviousHash` stored; if adopted, `AuditEntry.Hash` recomputation `VerifyChain()` MUST detect any tampered row (mismatch returns `Error.DataCorrupted`); if not adopted, ADR documents alternative controls (DB `REVOKE UPDATE/DELETE` for app role, row-level security, WORM storage). This FR is `SHOULD`, not `MUST` — either outcome satisfies spec if ADR exists.
- **FR-015**: System MUST expose write-side via `IRepository<AuditEntry>` exposing only `AddAsync(AuditEntry)` + `SaveChangesAsync` (no `Update`/`Remove`) and `IUnitOfWork` — enforced by `AuditEntry` having no public setters and `DbContext` configuring `AuditEntries` as `IsImmutable` simulation (no `Entry(entity).State = Modified` path compiles); integration test `AuditEntryIsImmutable` asserts attempted update is ignored or throws.
- **FR-016**: Audit search results MUST include before/after snapshots masked, never raw secrets — contract `AuditEntryResponse` includes `BeforeSnapshot`/`AfterSnapshot` as `JsonDocument` with `***` replacements; sensitive field list is per `IAuditMaskingPolicy` configuration and is extensible without code change (config `Audit:MaskedFields`).
- **FR-017**: Configuration changes MUST be auditable: any `PUT /api/configuration/*` or `PublishPromptVersion` or `ReviewPolicyChanged` that mutates `appsettings`/`PromptVersion`/`ReviewPolicy` MUST emit `ConfigurationChanged` `AuditEntry` with actor, resource (`ConfigurationKey`), before/after snapshots (masked if contains secrets), and correlation ID — consumers include prompt/config change handlers.
- **FR-018**: System MUST handle `AuditEventConsumer` idempotency at scale: consumer keys on `EventId` dedup table `audit_consumed_events(EventId PK, ProcessedAt UTC)` with `UNIQUE(EventId)` — duplicate `IntegrationEvent` delivery (at-least-once) returns success without side effect and without throwing; consumer is `IHostedService` background via `IEventBus` RabbitMQ topic `audit.*` with manual ack + exponential retries (at-least-once); performance: consumer handles 100 events/sec without duplicate entries.

### Key Entities

- **AuditEntry** (AggregateRoot/Entity, `AuditEntryId` StronglyTypedId<Guid>): `AuditId` (PK, Guid), `Timestamp` (DateTime UTC, required, indexed desc), `Actor` (`ActorReference` VO: `ActorId` Guid, `ActorType` User|System|Anonymous, `DisplayName` 1..200), `Action` (`AuditAction` Enumeration, 31 values R2 catalog, required), `ResourceType` (string 1..100, e.g., `Document`, `Project`, `WorkItem`, `LlmOperation`, `Configuration`), `ResourceId` (string 1..200, e.g., documentId, projectId), `OrganizationId` (Guid? nullable, from Organization Unit), `TenantId` (Guid, required, indexed — isolation), `Result` (`AuditResult` VO: `Success|Denied|Failed` + `ErrorCode` 1..100 optional), `CorrelationId` (Guid, required, indexed — from OTel), `ClientMetadata` (`IpAddress` IPv4/IPv6 1..45, `UserAgent` max 500, where permitted), `BeforeAfterSnapshot` (`BeforeAfterSnapshot` VO: `BeforeJson`/`AfterJson` jsonb, masked — sensitive `***`), `PreviousHash` (string? 64 hex if hash chaining enabled per ADR, else null), `Hash` (string? 64 hex if chaining), `OrganizationName` snapshot (string 1..200 masked). Immutable by design — no mutators, only constructor; append-only.
- **AuditAction** (Enumeration): 31 values per FR-002 (AuthenticationSucceeded..AuditCorrected) — covers R2 catalog; used as filter dimension in `SearchAuditEntries`.
- **ActorReference** (ValueObject): `ActorId` Guid (from JWT `sub` or `System` GUID `00000000-0000-0000-0000-000000000001` for system actions), `ActorType` `User|System|Anonymous` (Enumeration), `DisplayName` 1..200 (masked if needed). Value-equality.
- **ResourceReference** (ValueObject): `ResourceType` 1..100, `ResourceId` string 1..200 (Guid string or composite like `projectId/workItemId`). Value-equality.
- **BeforeAfterSnapshot** (ValueObject): `BeforeJson`/`AfterJson` (`JsonDocument` 1..50k, masked — sensitive keys `***`). `IAuditMaskingPolicy.Mask` replaces `ApiKey`/`Password`/`Secret`/`ConnectionString`/`Token`/`CreditCard` with `***` before persistence; `GetEqualityComponents` includes both JSON normalized.
- **AuditResult** (ValueObject): `Result` `Success|Denied|Failed` (Enumeration), `ErrorCode` string 1..100 optional (e.g., `Document.Forbidden`, `Auth.Failed`). Value-equality.
- **Domain Services**: `IAuditMaskingPolicy` (what is sensitive — pure, configurable via `Audit:MaskedFields`), `IAuditQueryAuthorization` (Golden Rule A composition for audit search — pure, returns `Expression<Func<AuditEntry,bool>>`).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001** (Catalog completeness): Given any action in the R2 catalog (22 distinct action types including `AuthenticationFailed`, `AuthorizationDenied`, `ProjectCreated`, `DocumentAccessDenied`, `LlmResultApproved`), when it occurs with `CorrelationId = C1`, Then exactly one `AuditEntry` exists within 2 seconds with `Actor` == performer (`sub` or `System`), `ResourceType/ResourceId` == target, `Result` == `Success|Denied|Failed`, `CorrelationId == C1`, and masked snapshot without sensitive leak — verified by `CatalogCompletenessTests` (22 actions × distinct actors) and per-action `SearchAuditEntries(filters: CorrelationId=C1)` returns 1.
- **SC-002** (Immutability): Given a persisted `AuditEntry` `E1`, when any supported code path attempts `E1.Action = "Tampered"` or `repository.Update(E1)` or `dbContext.Update(E1)` followed by `SaveChanges`, Then compilation fails (no setter) or runtime throws `NotSupportedException` and reload `GetAuditTrail(resourceId)` still shows original `Action` — verified by `AuditEntryIsImmutableTests` asserting no public mutator via reflection (`AuditEntry` has zero public setters and `IRepository<AuditEntry>` exposes only `AddAsync`).
- **SC-003** (Authorization-filtered search): Given an auditor `Auditor_A` scoped to subtree `OrgUnit_A` (and project `P_A` only), when they `SearchAuditEntries(filters: organizationId=Org_A, projectId=P_A)` where the tenant also has entries for `OrgUnit_B`/`P_B` (outside subtree), Then result contains zero entries for `P_B` and `GetAuditTrail(resourceId=P_B)` returns 404 shadow — verified by `CrossBranchAuditSearchTests` (5 actor types × 2 branches, assert `resultForForbiddenBranch == 0`, same filter as `IDocumentAccessPolicy` but scoped to audit `OrganizationId`).
- **SC-004** (Correlation timeline): Given a distributed document workflow with `CorrelationId = C1` spanning `HTTP POST /api/documents` (`DocumentUploaded`) → `DocumentProcessingStageCompleted(Validation)` → `DocumentProcessingStageCompleted(Storage)` → `LlmOperationQueued` → `LlmResultGenerated` → `LlmReviewCreated` (7 entries), When `GetOperationTimeline(correlationId=C1)` is called by any participant who can read the root document, Then the response returns those 7 entries ordered `Timestamp` asc with `Actor`, `Action`, `ResourceType/ResourceId`, `Result`, `BeforeAfterSnapshot` masked — reconstructing the full workflow — verified by end-to-end `CorrelationPropagationTests` with OTel baggage propagation `HTTP X-Correlation-Id → TenantContext → Activity → DomainEvent → IntegrationEvent → AuditEntry`.
- **SC-005** (Health per dependency): Given a critical dependency outage (e.g., `postgres` down with `Npgsql.SocketException` while `rabbitmq` healthy), When `GET /health` (readiness) is called, Then `HealthReport.Entries["postgres"] = Unhealthy` and `Entries["rabbitmq"] = Healthy` distinctly — failure is identifiable per dependency (not aggregated 503 alone) and `Entries["postgres"].Exception.Message` is `***`-masked but `Entries["postgres"].Status` is `Unhealthy` — verified by `HealthPerDependencyTests` (per-dependency fault injection for postgres/rabbitmq/redis/ai_provider/vector_store).

## Assumptions

- `IManagementHierarchy`, `IAuthorizationEvaluator`, `TenantContext` (SPEC-002/005/006) are available as Shared Kernel for audit query authorization; until ready, tests use in-memory fakes per BuildingBlocks `Specification<T>` patterns. Permission names consumed: `audit.search`, `audit.trail.read`, `audit.timeline.read`, `health.read`.
- `oroidentityserver` OIDC identity provides `sub` (Actor) and `tenant_id`; every command/query carries `actor`+`tenant`; anonymous access is always denied and is itself audited as `AuthenticationFailed` with `ActorType=Anonymous`.
- Audit emission path is domain events → `IOutboxWriter` (same tx as business write per `AppDbContextBase`) → `OutboxProcessor` polls `SELECT ... FOR UPDATE SKIP LOCKED` → `IEventBus` RabbitMQ topic `audit.*` + `integration_events` → `AuditEventConsumer` (`IHostedService` background, `IIntegrationEventHandler`, idempotent via `audit_consumed_events(EventId)` dedup table). At-least-once delivery, handler idempotent.
- `AuditEntry` table is `audit_entries` in schema `audit` (`HasDefaultSchema("audit")`, `IsImmutable` simulation) — no `UPDATE`/`DELETE` path compiled; corrections are new entries with `Action=AuditCorrected` and `BeforeAfterSnapshot` containing before/after of the correction. DB app role has `REVOKE UPDATE, DELETE ON audit_entries` per ADR if hash chaining not adopted.
- Hash chaining (R1 SHOULD) is evaluated in ADR (`ADR-007-01`): either adopt `SHA256(PreviousHash || AuditId || Timestamp || Action || Actor)` chaining with `PreviousHash`+`Hash` columns and `VerifyChain()` or document alternative controls (DB REVOKE, RLS, WORM). Both satisfy `SHOULD` if ADR exists — this spec does not mandate chaining, only its evaluation.
- Client metadata (IP, UserAgent) is captured where permitted by privacy (EU IP anonymization — last octet masked `192.168.1.xxx` if policy requires) and where `HttpContext` is available (background jobs have `null` IP but `System` actor).
- OTel propagation is via `Activity.Current.Baggage` (`CorrelationId`) + `AsyncLocal<TenantContext.CorrelationId>` + `IOutboxWriter.CorrelationId`; if incoming HTTP lacks `X-Correlation-Id`, middleware generates `Guid.NewGuid()` at request entry (`CorrelationIdMiddleware`) and propagates to all downstream `AuditEntry` rows.
- Pagination: `SearchAuditEntries` and `GetAuditTrail` use `page` 1..100, `pageSize` 1..100 (default 50, cap 100) plus `Link` header for next page; performance goal <300ms p95 for 1k entries paginated via composite index `(TenantId, Timestamp desc)` + `(ResourceType, ResourceId, Timestamp)`.
- Audit query authorization reuses Golden Rule A composition (tenant + subtree via `IManagementHierarchy` + project membership via `IProjectMembership` + explicit grants + `auditor`/`manager` role) — same `BuildAuthorizedFilter` as `IDocumentAccessPolicy` but scoped to `AuditEntry.OrganizationId`/`AuditEntry.ProjectId` snapshot taken at emission time.
- Dashboards: `AddServiceDefaults()` OTel `Metrics` (`http_requests_total`, `http_requests_failed_total{status, endpoint}`, `job_failed_total{job, stage}`, `rabbitmq_queue_depth`, `http_request_duration_ms` histogram) + `HealthChecks` (`/health` readiness per dependency, `/alive` liveness) + `Serilog` OTLP → Aspire dashboard `Metrics`/`Traces`/`Logs`; alerts (e.g., `health Unhealthy >1m` → Slack/Pager) are via ADR (`ADR-007-02` alerting backend choice: Prometheus AlertManager vs OTel alerts vs Grafana) — this spec only emits telemetry, not the alerting infrastructure.
- Sensitive mask list `Audit:MaskedFields` defaults to `ApiKey,Password,Secret,ConnectionString,Token,CreditCard,PrivateKey` — extensible via config without code change; `IAuditMaskingPolicy.Mask` replaces values with `***` before serialization to `BeforeAfterSnapshot`.
- Audit retention is per legal hold (`RetentionPolicy` analog) — entries are retained per tenant's compliance period (e.g., 7 years), hard purge, if ever, is a separate governance flow out of scope and requires explicit `PurgeAuditEntry` command with 4-eyes approval (not in this spec).
- `AuditEventConsumer` is the only writer to `audit_entries` — domain never writes directly to audit DB; all other BCs write to their own DB and emit via outbox; consumer runs as `Audit.Infrastructure` `BackgroundService` with manual ack + exponential retries.
- Optimistic concurrency is not applicable to `AuditEntry` (no updates), but `audit_consumed_events` `EventId` has `UNIQUE` constraint — concurrent duplicate delivery race on same `EventId` results in `UniqueConstraintViolation` which consumer catches and treats as success (idempotent).

## Dependencies & Traceability

- **Depends on**: SPEC-001 (all BCs emit domain→outbox→integration events for the R2 catalog — this spec is the universal consumer), SPEC-002 Identity/Organization (TenantContext, IManagementHierarchy, IAuthorizationEvaluator for query filtering), SPEC-005 Documents (Document* events + IDocumentAccessPolicy), SPEC-006 AI (Llm* events) — all prior specs 002..006 are producers for audit.
- **Enables**: BC-09 Compliance/Ratification (consumes `AuditEntry` for compliance reports + 4-eyes approval), platform audit API for SOC2/ISO exports, operator SRE dashboards for incident response.
- **Constitution**: Principles VIII (append-only, never mutate history, hash chaining SHOULD), XVIII (observability — OTel/Serilog/health, Aspire dashboard), XV (tenant/organization aware — 404 shadow), VII (hierarchical + Golden Rule A for audit search), VI (rules in domain — masking policy, query authorization), VIII + §Final Rule (explicitness), XX/XXI (testability + TDD/DDD/Vertical Slices), XXII (minimal-ui-design-system for dashboards, not API). §Audit Architecture (if exists) — explicit per-spec audit catalog.
- **ADRs required**: Hash chaining vs REVOKE controls (`ADR-007-01`), alerting backend (`ADR-007-02` — Prometheus/OTel/Grafana), audit retention/purge (`ADR-007-03`).
- **Skills**: `minimal-ui-design-system` (tokens, elevation, signals) for audit search/timeline dashboards and health dashboards — API contracts are agnostic of UI skill but dashboards MUST follow its tokens/elevation when built.

## Out of Scope

- Alerting infrastructure delivery (PagerDuty/Slack/OpsGenie, AlertManager rules) — this spec only emits health/metrics/OTel; alerting is via ADR and separate infra provisioning.
- Audit retention hard purge/GC and WORM storage provisioning — governance workflow beyond append-only; retention expiry only flags, not deletes.
- Cross-tenant audit sharing — explicitly denied; tenant isolation non-negotiable (Principle XV).
- End-to-end encryption of audit payload beyond TLS + at-rest DB encryption (assumed per SPEC-012) — field-level encryption of snapshots is future if needed, not this spec.
- Real-time push/WebSocket for audit tailing — poll/query via `SearchAuditEntries` only; streaming tail is separate.
- Cost/billing metering for audit volume — metering hooks may emit events but billing is separate BC.
- Hard physical deletion of audit rows for GDPR erasure — append a masked `AuditCorrected` entry; physical `DELETE` is separate governance with 4-eyes, not this spec's consumer path (consumer never deletes).
- Alert on audit tamper-evidence failure — detection is via `VerifyChain()` query, alerting on detection is via ADR-007-02.
