# Research: Identity, Access and Organization

**Feature**: 003-identity-access-organization | **Date**: 2026-08-31 | **Status**: Complete

No `NEEDS CLARIFICATION` markers were present in Technical Context after 002's foundation. The four decisions below resolve the only ADR-level choice points for this feature.

## Decision 1: Hierarchy Storage — Recursive CTE on Adjacency List (Phase 1)

- **Decision**: Store `ManagementRelationship` as an adjacency list (`manager_id → subordinate_id` rows with `type`, `valid_from/to`, `organization_unit_id`, `tenant_id`) in table `organization.management_relationships` (schema `organization` via `HasDefaultSchema("organization")` + `ToTable("management_relationships")` override). Implement `IManagementHierarchy` queries (`IsInSubtree`, `GetSubtree`, `GetAncestors`, `GetCommonAncestor`) with **PostgreSQL recursive CTEs** (`WITH RECURSIVE`) over that table, not a closure table or `ltree`.
- **Rationale**: Satisfies R4's ADR requirement (informed by `draft/discovery/000-repository-catalog.md` and research Decision 3 in 002). Recursive CTE keeps writes O(1) (single row per relationship) and leverages Postgres 15+ which OroKanban already uses via Aspire. Reads are O(depth) but depth is typically <10 and the 500 ms p95 target for 1,000 users is well within CTE performance with a `(tenant_id, manager_id)` index and a `(tenant_id, subordinate_id)` index. Closure table would be O(1) reads but O(N) writes on re-parenting and adds a second table to keep consistent; `ltree` would tie us to a Postgres extension. CTE is the lowest-operational-overhead choice that preserves the unbounded-depth invariant and can be migrated to a closure cache later without changing the domain contract.
- **Alternatives considered**: Closure table (rejected — write amplification, second table consistency); `ltree`/`ltree` extension (rejected — extension dependency, less portable, no benefit at this scale); in-memory only (rejected — violates persistence requirement).

## Decision 2: Subtree Cache — Redis with Explicit Invalidation on Integration Event

- **Decision**: Cache `GetSubtree(managerId)` and `IsInSubtree(managerId, userId)` results in Aspire `redis` (`StackExchange.Redis` via `BuildingBlocks.ServiceDefaults` `WithReference(redis)`) with key pattern `hierarchy:{tenant}:{managerId}:subtree` and `hierarchy:{tenant}:{managerId}:{userId}:isIn`. TTL 5 minutes. On `OrganizationHierarchyChangedIntegrationEvent` (published from `Organization.Infrastructure` via outbox), a `HierarchyCacheInvalidator` (in `Organization.Infrastructure`) deletes the affected manager's keys and all ancestor keys (computed via `GetAncestors`). On Redis unavailable, fall back to direct CTE query and log a warning — never fail authorization or bypass the check.
- **Rationale**: Satisfies R4's cacheable + explicit invalidation requirement and SC-005. Same pattern as 002's `docs/architecture/service-defaults.md` — Redis is already declared in AppHost. Explicit deletion (not TTL-only) makes `GetSubtree` reflect changes without restart, satisfying the acceptance scenario for hierarchy-change invalidation.
- **Alternatives considered**: No cache (rejected — 500 ms p95 would be tighter without it on larger hierarchies); TTL-only without explicit invalidation (rejected — stale reads violate SC-005); distributed cache via database (rejected — adds load to Postgres).

## Decision 3: Permission Catalog — Seeded, Not Hard-Coded, Role→Permission Map in Identity

- **Decision**: Permission catalog lives in `Identity.Domain` as a seeded set of `Permission` value objects (`PermissionCode` VO) inserted via an `IHostedService` seeder on first run (reads `PermissionsSeed.json` or a code-defined list). The catalog covers `project.read/create/update/delete`, `workitem.read/create/assign/update/complete`, `document.read/upload/classify/version/approve`, `ai.execute/review/approve`, `audit.read`, `organization.manage`. A `RolePermissionMap` table (also seeded) maps the 10 initial roles (`RootManager`, `Manager`, `Supervisor`, `Contributor`, `Reviewer`, `Auditor`, `DocumentManager`, `ProjectManager`, `AIReviewer`, `Administrator`) to permission sets. Roles themselves live in OroIdentityServer; the map is app-owned and extensible (add a `Permission` row + a `RolePermission` row, no code change to `IAuthorizationEvaluator`).
- **Rationale**: Directly satisfies R2 ("extensible, seeded, not hard-coded") and the discovery catalog's permission rows. Seeding via `IHostedService` keeps the catalog versioned and the `Identity.Infrastructure` DbContext as the owner, while roles stay in OroIdentityServer per Principle II. The evaluator consumes `IPermissionCatalog` via `Identity.Contracts` without storing roles.
- **Alternatives considered**: Hard-coded enum of permissions (rejected — violates R2's extensible/seeded requirement); storing roles in OroKanban (rejected — violates Principle II, roles belong to OroIdentityServer); storing the map in Redis (rejected — loses transactional consistency with grants).

## Decision 4: Authorization Evaluator Composition — Single Domain Service, Tenant-First

- **Decision**: `IAuthorizationEvaluator` is a single domain service in `Organization.Domain` (implemented in `Organization.Infrastructure` where it can access `IManagementHierarchy`, `IPermissionCatalog`, and `IProjectMembership` — the latter as a consumed interface/contract, not implemented here). Evaluation order is fixed: 1) tenant mismatch → deny (fastest, isolation first), 2) permission via `IPermissionCatalog` (role→permission), 3) ownership check, 4) subtree via `IManagementHierarchy`, 5) `ExplicitGrant` check, 6) `IProjectMembership` check, 7) classification check. Each step's deny reason is captured as an internal `DenyReason` enum, mapped to `authorization.denied` audit fields but never returned to the caller (caller sees only `Result` with generic `Forbidden`).
- **Rationale**: Satisfies R5's explicit inputs and R7's audited denials while keeping tenant isolation as the first gate (edge case: tenant mismatch denies before any subtree work). Single service makes the security matrix testable via `IsSatisfiedBy`-style unit tests and mirrors 002's `Result`/`Error` pattern (deny → `Error.Forbidden`). Explicit grant and project membership are the only cross-branch exceptions (R6).
- **Alternatives considered**: Multiple evaluators per resource type (rejected — fragments Golden Rule A, harder to audit); tenant check last (rejected — leaks cross-tenant existence before denying); returning deny reasons to callers (rejected — violates R5 "never leaked").
