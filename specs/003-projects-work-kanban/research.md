# Research: Projects, Work Items and Kanban

**Feature**: 003-projects-work-kanban | **Date**: 2026-09-01 | **Status**: Complete

No `NEEDS CLARIFICATION` markers were present in Technical Context after Phase 0 evaluation. The five decisions below resolve the only ADR-level choice points for BC-03; each follows the BuildingBlocks canon (`draft/libraries/buildingblocks.md`) and reuses conclusions from 002 where applicable.

## Decision 1: WorkItem Hierarchy Storage — Adjacency List + Recursive CTE (reuses 002 pattern)

- **Decision**: Store `WorkItem.ParentId` as a nullable self-FK adjacency list (`work_items.parent_id` FK `work_items.id`, indexed) in table `projects.work_items` (`ProjectsDbContext : AppDbContextBase` with `HasDefaultSchema("projects")`). No closure table, no `ltree`. Ancestor/descendant queries (reparenting validation, epic swimlane grouping, progress aggregation) use **PostgreSQL recursive CTEs** (`WITH RECURSIVE`) either as raw SQL via `FromSqlRaw` for ancestry or as EF-translatable `IQueryable` recursion wrapped in a domain service; the domain rule `ReparentNoCycleRule` calls `IHierarchyInspector.GetDescendantIds(itemId)` (implemented in Infrastructure with CTE) to reject reparenting to a descendant.
- **Rationale**: Directly satisfies R3 (arbitrary depth via same aggregate, reparenting validated) and the discovery catalog's recursive CTE preference from 002 (Decision 1 for `ManagementRelationship`). Writes remain O(1) (single `ParentId` column), which matters for Kanban drag/drop and reparenting. Reads O(depth) are bounded — product depth is <10 levels (Epic→Feature→Task→Subtask) and a `(project_id, parent_id)` index plus `(tenant_id, project_id)` index keeps CTEs under 50 ms at the 50–1,000 item scale targeted by SC-007. Reuses the proven 002 pattern so board/developer knowledge transfers; can migrate to a closure cache later without changing the `WorkItem` aggregate or `ParentId` contract.
- **Alternatives considered**: Closure table (rejected — second table to keep consistent on every reparent, N-write amplification, no benefit at this scale); `ltree` extension (rejected — extension dependency, less portable, overkill for adjacency queries that CTE already handles); materialized path string (rejected — string parsing fragility, reparent requires rewriting entire subtree path).

## Decision 2: WorkItemStatus Transition Map — Enumeration + In-Memory Policy Map Backed by CheckRule

- **Decision**: `WorkItemStatus` is an `Enumeration` subclass seeded with `Backlog(1)`, `Planned(2)`, `InProgress(3)`, `Blocked(4)`, `InReview(5)`, `Completed(6)`. Allowed edges are a read-only `IReadOnlyDictionary<int, IReadOnlySet<int>> AllowedTransitions` owned by `IWorkItemTransitionPolicy` (implemented as `WorkItemTransitionPolicy` in `Projects.Infrastructure`, injected into `Projects.Domain` via `IWorkItemTransitionPolicy` contract). Map shipped: `Backlog->{Planned}`, `Planned->{InProgress}`, `InProgress->{Blocked, InReview}`, `Blocked->{InReview, InProgress}`, `InReview->{Blocked, Completed}`, `Completed->{InProgress (reopen)}` per `IWorkItemTransitionPolicy`. Reopen edges (`Completed->InProgress`, optionally `Completed->Backlog`) are configurable via options and gated by evaluator role check. Every `ChangeWorkItemStatus` handler calls `workItem.CheckRule(new TransitionIsAllowedRule(current, target, transitionPolicy))` which consults the map; `WorkItem.ChangeStatus` is the only mutation method and enforces it. Unit tests enumerate 6×6=36 pairs exhaustively.
- **Rationale**: Satisfies R4 and Principle XIV — single map, domain-owned, exhaustively testable, never UI-driven. `Enumeration` per BuildingBlocks already gives stable IDs and seed rows; the policy object makes reopen rules configurable without editing the aggregate (avoids hard-coded `if` chains). `CheckRule` pattern keeps the rule in `IBusinessRule` shape required by Principle VI and mirrors `SubtreeCannotContainManagerRule` from 002.
- **Alternatives considered**: State Machine library (Stateless) (rejected — extra dependency, hides the map, violates "rules belong to domain" canon that prefers `IBusinessRule`); database trigger check (rejected — violates VI, not testable via unit `IsSatisfiedBy`); per-status subclass/Strategy pattern (rejected — hard-coded classes violate R2/R4 taxonomy-must-be-configurable).

## Decision 3: Dependency Cycle Detection — Domain Graph DFS over Blocks/DependsOn Only

- **Decision**: `IDependencyCycleDetector.HasCycle(allEdges, candidateEdge)` is a pure domain service (no EF, no IO) operating on `IReadOnlyList<WorkItemDependency>` edges for the same `project_id`. It runs a DFS (iterative, O(V+E)) over the directed graph formed by edges whose `type` is `Blocks`/`BlockedBy`/`DependsOn` — `RelatedTo` edges are filtered out before traversal. `BlockedBy` is the inverse view of `Blocks` (single stored direction `dependent→principal` with `type=Blocks`; query-time flip produces the `BlockedBy` view). `AddDependency` handler: 1) validate intra-project (or `RelatedTo`-only cross-project per assumption), 2) load existing non-`RelatedTo` edges for the project via repository `Specification`, 3) call detector with existing + candidate, 4) if cycle → `CheckRule(CircularDependencyRule)` fails → `Result.Error(Validation, "Circular dependency")` and no insert; else insert + raise `DependencyAdded`. Concurrency: step 2–4 inside the same `unitOfWork` transaction with repeatable-read isolation; second racing insert will see the first's committed edge and be rejected (see edge case 10). No Redis needed.
- **Rationale**: Satisfies R5's `IDependencyCycleDetector` + `CircularDependencyRule` + `RelatedTo` exclusion + partial `Blocked` derivation. Keeping detection in-domain (pure function) matches 002's grant-expiry/reparent rule pattern and is the only place the rule is evaluated (FR-023). DFS is sufficient for project-scoped graphs (<1,000 edges); BFS/stack overflow is avoided with iterative loop. Loading edges per-project bounds the set; for very large projects, a DB-level recursive CTE cycle check can replace the in-memory traversal later without changing the domain contract.
- **Alternatives considered**: DB recursive CTE cycle check per insert (considered as future optimization but not needed for MVP — in-memory is simpler, deterministic, and testable without DB); graph DB (rejected — new infrastructure, violates minimal-resources decision from 002); allow all cycles and derive `Blocked` lazily (rejected — violates invariant, would require UI to handle cycles).

## Decision 4: Assignment via IAssignmentPolicy Composing IManagementHierarchy + Project Membership

- **Decision**: `IAssignmentPolicy.CanAssign(assignerId, assigneeId, projectId, tenantId, ct)` is a domain service in `Projects.Domain` (implemented in `Projects.Infrastructure` where it can inject `IManagementHierarchy` from `Organization.Contracts` + `IProjectMembership` thin adapter + `IUserStateChecker.IsActive(userId)`). Order: 1) `workItem.Status != Completed` (else `WorkItemNotCompletedRule`), 2) `IUserStateChecker.IsActive(assigneeId)` (else validation error), 3) tenant matches (delegated to evaluator), 4) `IsInSubtree(assignerId, assigneeId)` OR `IProjectMembership.IsMember(assigneeId, projectId)` AND `IsMember(assignerId, projectId)` — both sides of the shared-membership branch must be members. `AssignWorkItem` handler composes `IAuthorizationEvaluator` (permission `workitem.assign` + classification/ownership) before `IAssignmentPolicy`; deny reasons are internal, caller sees generic `Forbidden` and an audit `authorization.denied` is outboxed. Success raises `WorkItemAssigned`/`WorkItemReassigned` + audit + `WorkItemAssignedIntegrationEvent`.
- **Rationale**: Satisfies R6 and Golden Rule A feed from R1 — the only place "who can assign whom" is decided (FR-023). Reuses `IManagementHierarchy` Shared Kernel from 002 exactly as its contract prescribes; adding a second implementation would duplicate 002's CTE/Cache logic. `IProjectMembership` is the thin adapter over `ProjectsDbContext.project_members` (read-only, no cross-module Infra ref — only a SQL view/projection inside Projects). Keeps the policy testable with `NSubstitute` fakes per 002's evaluator tests (subtree/membership matrix).
- **Alternatives considered**: Re-implement hierarchy locally in Projects (rejected — duplicates Organization, violates V modular boundaries); put assignment rule in `WorkItem` aggregate directly (rejected — would require aggregate to know `IManagementHierarchy`, breaking aggregate anonymity; better as domain service); in-controller check (rejected — violates VI).

## Decision 5: Concurrency, Persistence, and Kanban Read Model — RowVersion + EF Projection with Authorization Specification

- **Decision**:
  - **Concurrency**: `WorkItem.Version` is an `int` property mapped to a PostgreSQL `xmin`-independent `byte[] RowVersion` concurrency token via EF Core `IsConcurrencyToken()` (or `IsRowVersion()` on Npgsql `bytea`) plus a separate exposed `Version` integer incremented by `WorkItem` on each mutation (`Version++` inside `ChangeStatus/Assign/Reparent/Complete`). The API accepts `expectedVersion` (body) or `If-Match` header; the handler loads with `Version == expected` check and relies on EF's `DbUpdateConcurrencyException` → `Error.Conflict("Concurrency conflict")` → HTTP 409 via `Result→HTTP` (per Principle XVI). No silent overwrite, never returns 5xx on stale write.
  - **Persistence**: Single `ProjectsDbContext : AppDbContextBase` owns `projects.work_items` (`RowVersion` column, owned `Tag` collection as `jsonb` or join table `project_work_item_tags`), `projects.projects`/`project_members`/`project_milestones`, `projects.work_item_dependencies` (composite unique `(dependent_id, principal_id)` preventing duplicate edges), enumeration tables for seeded `WorkItemStatus/Type/Priority/Criticality/DependencyType`. Schema `projects` via `HasDefaultSchema("projects")` + per-entity `ToTable`. Outbox via `OutboxEntityTypeConfiguration` inherited from `AppDbContextBase`.
  - **Kanban read model**: Pure EF projection — `GetKanbanBoardQueryHandler` builds `IQueryable<WorkItem>` filtered by `projectId` + query `Specification` (`AuthorizedWorkItemSpec` composing subtree `Specification<T>` from `IManagementHierarchy` + project-membership check before `Where` so authorization is in SQL, never post-fetch), then filters `status/assignee/epic/priority/criticality/tags/dueDateRange`, applies sorting (`ORDER BY criticality DESC, priority, dueDate, updatedAt`), paginates, and groups in-memory (or in SQL with window) into `BoardColumn { status, count, items }` and optional `Swimlane { key, columns }` for `swimlane=assignee|epic`. `epic` swimlane resolves root Epic via recursive CTE ancestry (same adjacency pattern as Decision 1). `DueDate` overdue indicator is computed per-row `DueDate < DateTime.UtcNow && status != Completed`. No separate read DB, no direct board mutation endpoint.
- **Rationale**: Satisfies R7 (board never mutates — no `ICommand` on board query, only `IQuery`), FR-020 (optimistic concurrency), FR-021 (authorization before fetch), and SC-004/SC-007/SC-008 performance bounds. RowVersion + Version integer matches constitution "Optimistic concurrency where appropriate" and 002's `RowVersion` convention. Tag as `jsonb` vs join table is an implementation detail left to the handler — both satisfy EF; quickstart prefers join table for tag filtering via `Specification` unless benchmarking shows `jsonb` wins. Authorization composition before fetch uses the same `Specification<T>.And` pattern verified in 002 so board results never leak cross-branch data.
- **Alternatives considered**: Pessimistic locking (rejected — unnecessary contention for Kanban drag/drop); ETag-only without Version (rejected — loses increment semantics needed for audit trace: which version was overwritten); separate CQRS read store/EventStore (rejected — extra projection pipeline, violates minimal 002 stack; can add later if board exceeds EF performance); returning raw entities to frontend (rejected — violates XVI, entities must not become API contracts).
