# Research: Audit, Monitoring and Compliance

**Feature**: 007-audit-monitoring-compliance | **Date**: 2026-09-01 | **Status**: Complete

No `NEEDS CLARIFICATION` remained — all technical choices are informed by `draft/libraries/buildingblocks.md` + constitution Principles VIII/XVIII + existing modules `Audit` stub + `Organization`/`Documents`/`AiProcessing` + `BuildingBlocks.ServiceDefaults` OTel.

## Decision 1: Append-only audit store with immutability via domain + EF + DB REVOKE (hash chaining evaluated per ADR, not mandated)

- **Decision**: `AuditEntry` is `AggregateRoot<AuditEntryId>` (`StronglyTypedId<Guid>`) but **conceptually immutable**: domain exposes **no public setters** (constructor only, `init` where needed, zero `Update` mutators); `IRepository<AuditEntry>` (EfRepository) exposes only `AddAsync(AuditEntry)` + `UnitOfWork.SaveChangesAsync` (no `Update`/`Remove` methods even exist on the interface — compile-time impossibility); `AuditDbContext : AppDbContextBase` has `HasDefaultSchema("audit")` and configures `AuditEntries` with `UsePropertyAccessMode(PropertyAccessMode.Field)` + `HasNoKey`? not, but with `IsImmutable` simulation: `OnModelCreating` does **not** map any `Update` behavior, and `ChangeTracker` is never put in `Modified` for `AuditEntry` (architecture test asserts `AuditEntry` has zero public setters via `typeof(AuditEntry).GetProperties().Where(p=>p.SetMethod?.IsPublic==true).Count==0` and `IRepository<AuditEntry>` has only `AddAsync`). For DB hardening, two alternative controls evaluated per `ADR-007-01` (`SHOULD`): **Option A** (chosen for R1 `SHOULD`): hash chaining `AuditEntry.Hash = SHA256(PreviousHash || AuditId || Timestamp.ToString("O") || Action || ActorId)` + `PreviousHash` stored (computed in same transaction with `SELECT ... FOR UPDATE` on tail entry to serialize concurrent writers, `PreviousHash` of first entry is `0…0`). **Option B** (fallback if chaining not adopted): `REVOKE UPDATE, DELETE ON audit.audit_entries FOR app_orokanban` + RLS. Either satisfies `SHOULD` if ADR exists; current implementation proceeds **without chaining** by default (DB REVOKE) and documents chaining as `ADR-007-01` evaluated but not implemented — `VerifyChain()` is a future query, not a blocking feature. Corrections are new rows `Action=AuditCorrected, ResourceId=correctedAuditId, BeforeAfterSnapshot={Before: oldResult, After:newResult}` + new `Timestamp`, not `UPDATE`. `PreviousHash`/`Hash` columns are nullable `string 64 hex` for future chaining; present schema includes them but default `null` until ADR adopts chaining.
- **Rationale**: Satisfies R1 (never updated/deleted, corrections new entries, `SHOULD` via ADR not `MUST`) + Principle VIII (append-only, tamper-evident evaluated). Domain immutability (no setters) is stronger than DB alone — it fails at compile, not just at runtime SQL. DB REVOKE is cheaper than hash chain for MVP and keeps `audit_consumed_events` dedup simple (no tail lock contention on high volume 100 events/sec). Hash chain is kept as ADR-evaluated alternative because it gives cryptographic tamper-evidence without WORM, but it adds per-insert tail lock and `VerifyChain()` cost; deferring insert-side compute until compliance explicitly requires it keeps MVP performance <300ms p95 for 1k paginated.
- **Alternatives considered**: DB `TRIGGER` that `RAISE EXCEPTION` on `UPDATE/DELETE` (rejected — trigger hides failure as runtime exception, not compile-time, and is harder to test via NetArchTest); WORM storage (e.g., `S3 Object Lock`) for audit payload (rejected — out of scope per spec, separate governance); pure hash chain without DB REVOKE (rejected — chain alone still allows root to `DELETE` and recompute chain offline, so DB REVOKE is still needed as complementary control).
- **ADR**: `ADR-007-01` records hash chaining vs `REVOKE` decision, hash `SHA256(PreviousHash||AuditId||Timestamp||Action||Actor)`, tail lock `SELECT ... FOR UPDATE`, and `VerifyChain()` `Error.DataCorrupted` contract. Spec's `PreviousHash`/`Hash` nullable columns are forward-compatible with either outcome.

## Decision 2: Emission path `domain→outbox→integration→audit consumer` idempotent via `audit_consumed_events(EventId)` dedup

- **Decision**: Every business DB (`OrganizationDbContext`, `ProjectsDbContext`, `DocumentsDbContext`, `AiProcessingDbContext`) already uses `AppDbContextBase` + `OutboxEntityTypeConfiguration` (`outbox_messages` table added by `base.OnModelCreating` via `BuildingBlocks.Kernel.Infrastructure`). Business write (e.g., `DocumentApproved` in `DocumentsDbContext`, `ProjectCreated` in `ProjectsDbContext`, `LlmResultApproved` in `AiProcessingDbContext`) is in same transaction as `IOutboxWriter.StageAsync(IntegrationEvent)` (JSON-serialized `IntegrationEvent` with `EventId=Guid.NewGuid()` + `OccurredOnUtc=DateTime.UtcNow` + `CorrelationId` from `Activity.Current.Baggage` or `TenantContext.CorrelationId`). `OutboxProcessor` (hosted service from `BuildingBlocks.Kernel.Infrastructure`, polling `SELECT ... FOR UPDATE SKIP LOCKED` from `outbox_messages` where `ProcessedOn IS NULL`) publishes to `RabbitMQ` via `IEventBus` (`BuildingBlocks.EventBus.RabbitMQ`, topic exchange `integration_events`, durable, publisher confirms) to topic `audit.<action>` (e.g., `audit.document.approved`, `audit.project.created`) **and** to `audit.*` wildcard for the `Audit` consumer. Consumer is `Audit.Infrastructure` `AuditEventConsumer : BackgroundService` that hosts `IEventBus` subscription to `audit.*` with `IIntegrationEventHandler<IntegrationEvent>` generic or per-action handlers (`IIntegrationEventHandler<DocumentApprovedIntegrationEvent>` etc.) that are all funneled to one method `HandleAsync(IntegrationEvent @event, CancellationToken ct)`: it first `SELECT 1 FROM audit.audit_consumed_events WHERE EventId=@event.Id FOR UPDATE` — if exists, return success (duplicate); else `INSERT INTO audit.audit_consumed_events (EventId, ProcessedAt) VALUES (@event.Id, $now)` in same `AuditDbContext` transaction as `INSERT INTO audit.audit_entries (...) VALUES (...)` (with `AuditId=Guid.NewGuid()`, `Timestamp=UtcNow`, `Action` mapped from `IntegrationEvent` type via `AuditAction.FromIntegrationEventType`, `Actor` from `IntegrationEvent.ActorId` or `System`, `CorrelationId=@event.CorrelationId ?? TenantContext.CorrelationId ?? Activity.Baggage`). Background service uses `IEventBus` manual ack + exponential retries (at-least-once, `Polly` 3 retries): distinct `EventId` dedup + `audit_consumed_events(EventId PK UNIQUE)` handles concurrent duplicate delivery race (`UniqueConstraintViolation` caught and treated as success). Consumer handles 100 events/sec (batch `Take(10)` from outbox, `Task.WhenAll`). `CorrelationId` is propagated: middleware `CorrelationIdMiddleware` at `Api` `Program.cs` does `if (!Request.Headers.TryGetValue("X-Correlation-Id", out var cid)) cid=Guid.NewGuid().ToString(); Activity.Current?.SetBaggage("CorrelationId", cid); TenantContext.CorrelationId=Guid.Parse(cid); Response.Headers["X-Correlation-Id"]=cid;` — this `TenantContext.CorrelationId` is read by every Handler's `IOutboxWriter.CorrelationId` and every `DomainEvent.CorrelationId` (added to `IDomainEvent` via `Activity.Baggage`).
- **Rationale**: Satisfies R3 (domain→outbox→integration→audit consumer idempotent, CorrelationId from OTel) + Principle XVII (async via outbox+RabbitMQ, at-least-once, idempotent via `EventId` dedup) + catalog R2 (every `DomainEvent` maps to one `AuditAction` per `ADR-007-02` mapping table). Reuses existing `BuildingBlocks.Kernel.Infrastructure` outbox (no new infrastructure) — `Audit` is the **only** dedicated consumer/writer to `audit.audit_entries`; other BCs never write to `audit` schema (enforced by Arch test `AuditOnlyWritesToAuditSchema`). Dedup on `EventId` (stable `Guid` per `IntegrationEvent`) is stronger than `(ResourceType,ResourceId,Action,CorrelationId)` composite because `EventId` is globally unique per `IntegrationEvent` instance, while composite would collide on retry of same logical action with same correlation but different business attempt (e.g., two `DocumentApproved` for same document but different `EventId`s legitimately should create two entries — composite would incorrectly dedup the second).
- **Alternatives considered**: Direct synchronous `INSERT` into `audit_entries` from business `DbContext` (rejected — couples audit to business transaction, violates V modular architecture, audit would be `DbContext` cross-reference, and business rollback would lose audit); CDC `Debezium` from `outbox_messages` (rejected — adds infra complexity, outbox already has `OutboxProcessor`); composite key dedup `(ResourceId+Action+CorrelationId)` only (rejected — see rationale, would under-count legit same-resource distinct events). Chose `EventId` PK dedup.
- **ADR**: `ADR-007-03` records emission path, dedup key `EventId`, topic `audit.*`, `CorrelationId` propagation `X-Correlation-Id → Activity.Baggage → DomainEvent → IntegrationEvent → AuditEntry`.

## Decision 3: Audit search `SearchAuditEntries` authorization-filtered via `IAuditQueryAuthorization` composing Golden Rule A pre-filter (tenant+subtree+project+grant before fetch)

- **Decision**: `IAuditQueryAuthorization` is a **pure domain service** (no I/O except injected `IManagementHierarchy.IsInSubtree(ancestorId, descendantId)` + `IProjectMembership.IsMember(projectId, userId)` + `IRepository<AuditEntry>` read for explicit grants? actually `AuditEntry` itself contains `OrganizationId`/`ProjectId` snapshot, so filter can be built from actor's authorized scope). Implementation `AuditQueryAuthorizationService` (in `Audit.Infrastructure`) implements two methods: `bool CanActorQuery(Guid actorId, Guid tenantId, SearchFilters filters)` and `Expression<Func<AuditEntry,bool>> BuildAuthorizedFilter(Guid actorId, Guid tenantId)` that composes: `audit.TenantId==tenantId` **AND** `(audit.OrganizationId==null || audit.OrganizationId IN authorizedOrgIds)` where `authorizedOrgIds = { tenantRootOrgId } ∪ subtree(actorId)` via `IManagementHierarchy.GetSubtreeIds(actorId)` (bounded to tenant) **AND** `(audit.ProjectId==null || audit.ProjectId IN authorizedProjectIds ∪ explicitGrants)` where `authorizedProjectIds` from `IProjectMembership.GetProjectIds(actorId)` plus `explicitGrants` from `documents.document_explicit_grants` (read via `IProjectMembership`? or direct query on `ExplicitGrant` table read-only). This `Expression` is passed to `EfRepository.FindAsync(Specification<AuditEntry>)` where `Specification<AuditEntry>` has `Where(BuildAuthorizedFilter)` + `Where(ActorId==filters.ActorId)` etc., so **fetch is pre-filtered** — no post-filter leak (same pattern as `IDocumentAccessPolicy` but scoped to `AuditEntry.OrganizationId` snapshot, not live `Document`). `Auditor` role (`auditor`/`manager` claim via `IAuthorizationEvaluator.CanActorPerform(actor, "audit.search")`) grants tenant-wide where `authorizedOrgIds = all orgs in tenant`; without that role, `authorizedOrgIds = subtree(actorId)` (branch-scoped, cross-branch filtered out per SC-003). `SearchAuditEntries` query handler (`SearchAuditEntriesQueryHandler : IQueryHandler<SearchAuditEntriesQuery, Result<Paged<AuditEntryResponse>>>`) first calls `IAuditQueryAuthorization.CanActorQuery` (if false → `Error.Forbidden` but also appends `AuditSearchDenied` audit of the search attempt via same-tx outbox — then maps to 403/404), then builds `Specification<AuditEntry>` with `BuildAuthorizedFilter` + filter predicates (`ActorId?`, `Action?`, `ResourceType?`, `ResourceId?`, `ProjectId?`, `OrganizationId?`, `DateRange.From/To`, `Result?`, `CorrelationId?`), applies `ApplyOrderByDescending(a=>a.Timestamp)` + `ApplyPaging(skip,take)` + `AsNoTracking`, executes via `SpecificationEvaluator`, maps to `AuditEntryResponse` DTOs (never domain entities) with `BeforeAfterSnapshot` already masked. Same `BuildAuthorizedFilter` is reused for `GetAuditTrail` and `GetOperationTimeline` (the latter filters `CorrelationId==filters.CorrelationId` + `TenantId` + authorized `OrganizationId` set). Pagination `page` 1..100, `pageSize` 1..100 default 50 cap 100, `Link` header for next page derived from `totalCount` vs `skip+take`.
- **Rationale**: Satisfies R4 (filter by actor/action/resource/project/org/date/result/correlationId, Golden Rule A filtered) + Principle XV (tenant/organization aware, 404 shadow cross-branch) + Principle VII (hierarchical, unbounded depth via `IManagementHierarchy`). Pre-filter before fetch is critical — post-filter would `SELECT * FROM audit_entries WHERE TenantId=@t` then filter in memory, leaking cross-branch rows to app memory and violating least-privilege + performance (<300ms for 1k). Pure domain service keeps `CrossBranchAuditSearchTests` testable via fakes (`IsInSubtree` stub that returns false for branch B when actor is in branch A) without DB. Mirrors `IDocumentAccessPolicy` OR semantics for consistency, but scoped to audit snapshot.
- **Alternatives considered**: Separate per-entry ACL table for audit (rejected — audit snapshot already has `OrganizationId`/`ProjectId` from business event, no need for live ACL join); RLS `CREATE POLICY` on `audit_entries` for tenant/organization (rejected — RLS is DB-only, not testable via pure `IAuditQueryAuthorization`, and would not compose with `IManagementHierarchy` dynamic subtree without `SECURITY DEFINER` function complexity). Chose pure `Expression` composition.
- **ADR**: `ADR-007-04` records `IAuditQueryAuthorization` interface, filter composition `TenantId AND (OrganizationId IN subtree OR ProjectId IN authorizedProjects)`, pagination, and cross-branch test matrix 5 actor types × 2 branches.

## Decision 4: Before/After snapshot masking via `IAuditMaskingPolicy` pure, config `Audit:MaskedFields` extensible without code change

- **Decision**: `IAuditMaskingPolicy { BeforeAfterSnapshot Mask(BeforeAfterSnapshot raw); }` pure domain service (no I/O). `BeforeAfterSnapshot` is `ValueObject` (`BeforeJson` `JsonDocument` 1..50k? `string` jsonb, `AfterJson` same). Implementation `AuditMaskingPolicy` (in `Audit.Infrastructure`) reads config `Audit:MaskedFields` (`string[]` default `ApiKey,Password,Secret,ConnectionString,Token,CreditCard,PrivateKey` — comma-split, case-insensitive) via `IOptions< AuditOptions>` (`AuditOptions.MaskedFields`). `Mask` does depth-first traversal of `JsonDocument` (via `System.Text.Json.JsonDocument.Parse` + `Utf8JsonWriter` re-serialize): for each `JsonProperty` where `property.Name` equals any `maskedField` (case-insensitive, exact match, no substring), replace `Value` with `JsonValueKind.String` `"***"` (preserving type as string masking, not `null`). For nested objects, recurse; for arrays, iterate elements. `BeforeJson` and `AfterJson` are each masked independently (same key list). Raw unmasked `BeforeJson`/`AfterJson` never leave business `AuditEventConsumer` — consumer calls `Mask` before `new AuditEntry(..., beforeAfterSnapshot: maskedSnapshot, ...)` and `IRepository<AuditEntry>.AddAsync` persists **only** masked JSON. `IAuditMaskingPolicy` is configurable per `ResourceType`? No — single global list per tenant (simpler, per spec scalable without code change — if per-ResourceType needed later, `Mask` overload `Mask(snapshot, ResourceType)` can be added without breaking existing). Unit `MaskingPolicyTests` asserts `Snapshot["ApiKey"] == "***"` for each masked key and `Snapshot["ContentHash"] == original` for non-masked (e.g., document `ContentHash` is not secret, so not masked). `AuditEntryResponse` DTO exposes `BeforeSnapshot`/`AfterSnapshot` as `JsonDocument` already masked (never raw).
- **Rationale**: Satisfies FR-004/FR-016 + R1 snapshot masked + Principle XIX (secret isolation, no `ConnectionString` leak) + Principle VI (rule in domain, pure). Config `Audit:MaskedFields` extensible without code change satisfies spec's "extensible without code change". Depth-first JSON traversal handles nested `BeforeJson` (e.g., `ConnectionString` inside `Settings` object) — flat key check would miss nested.
- **Alternatives considered**: DB `TRIGGER` that replaces `ApiKey` on `INSERT` (rejected — trigger is not pure/domain-testable, hides masking as DB side effect, and `IAuditMaskingPolicy` unit tests would not catch trigger miss); per-column `ENCRYPT` for snapshot (rejected — field-level encryption is future per Out-of-Scope, not this spec). Chose pure `ValueObject` + `IAuditMaskingPolicy`.
- **ADR**: `ADR-007-05` records masked fields default list, traversal algorithm, and config `Audit:MaskedFields`.

## Decision 5: Operational dashboards via `AddServiceDefaults()` OTel + HealthChecks + Aspire dashboard (alerts via ADR, not infra)

- **Decision**: No new Aspire container for audit dashboards — reuse `BuildingBlocks.ServiceDefaults.AddServiceDefaults()` already wired in `Api` `Program.cs` (`AddServiceDefaults()` adds `AddOpenTelemetry` + `AddHealthChecks` + `AddServiceDiscovery` + `AddHttpClient` resilience). This feature **adds per-dependency `AddHealthChecks` registrations** (in `Api` `Program.cs` or `Audit.Infrastructure` `ServiceCollectionExtensions`, discovered via `AddHealthChecks()` fluent): `AddCheck<NpgsqlHealthCheck>("postgres")` (`NpgsqlConnection` `SELECT 1` with `***`-masked `ConnectionString`), `AddCheck<RabbitMqHealthCheck>("rabbitmq")` (`RabbitMQ.Client` `CreateConnection` ping), `AddCheck<RedisHealthCheck>("redis")` (`StackExchangeRedis` `PingAsync`), `AddCheck<AiProviderHealthCheck>("ai_provider")` (`IChatClient` stub `GetResponseAsync("ping")` with `Temperature=0` + `MaxOutputTokens=1` timeout 2s), `AddCheck<VectorStoreHealthCheck>("vector_store")` (`VectorStore` count query). Each implements `IHealthCheck` (`Microsoft.Extensions.Diagnostics.HealthChecks`) with `HealthCheckResult Healthy|Unhealthy` + `Exception` (message `***`-masked for secrets, e.g., `NpgsqlException: ***`). `GET /health` (readiness) is `app.MapHealthChecks("/health", new HealthCheckOptions { ResponseWriter = UIResponseWriter.WriteHealthCheckUIResponse })` → `200 Healthy` when all `Entries` are `Healthy`, `503 Unhealthy` when any is `Unhealthy` (distinct per `Entries["postgres"]` vs `Entries["rabbitmq"]` — not aggregated alone, satisfies SC-005). `GET /alive` (liveness) is `app.MapHealthChecks("/alive", new HealthCheckOptions { Predicate = _ => false })` or `AddCheck("self")` only — always `Healthy` unless process dead. Metrics via `System.Diagnostics.Metrics` (`Meter` `OroKanban.Metrics`): `http_requests_total` (`Counter<long>` with tags `endpoint`, `tenantId`), `http_requests_failed_total` (`Counter` with `status` `403`/`500` + `endpoint`), `job_failed_total` (`Counter` with `job="document_processing"|"ai_processing"`, `stage="VirusScan"|"Embedding"`), `rabbitmq_queue_depth` (`ObservableGauge` via `RabbitMqHealthCheck` queue depth), `http_request_duration_ms` (`Histogram<double>` with `endpoint`). Logs via `Serilog` OTLP to `BuildingBlocks.Logger` (already wired) → Aspire dashboard `Logs` + `Traces` (OTel `ActivitySource` `OroKanban.Api`). Aspire dashboard `Metrics`/`Traces`/`Logs` shows `QueueDepth` gauge for `document_processing` and `ai_processing` topics, latency histogram for `QueueLlmOperation`. Alerts are **not** infra in this spec — they are `ADR-007-02` (choice: `Prometheus` `AlertManager` vs `Grafana` vs OTel `alerts` topic) — this spec only emits metrics/health, not the alerting rules/infra itself (per Out-of-Scope, alerts via ADR).
- **Rationale**: Satisfies R5 + FR-010/FR-011 + Principle XVIII (observability mandatory — `AddServiceDefaults()` OTel flow, `Activity.Baggage` `CorrelationId` correlates `HTTP → DomainEvent → IntegrationEvent → AuditEntry`), reuses existing BuildingBlocks (no new observability stack). Per-dependency `IHealthCheck` satisfies SC-005 identifiable failure (not aggregated `Unhealthy` alone). Metrics `job_failed_total` etc. give operator immediate `FailedRetryable` visibility for `DocumentProcessingJob`/`LlmOperation`.
- **Alternatives considered**: New Grafana/Prometheus container in AppHost (rejected — out of scope per spec, alerting infra is ADR, not spec); `Aspire.Hosting` `AddSeq`/`AddLoki` for traces (rejected — `AddServiceDefaults()` console OTLP already surfaces in Aspire dashboard, Seq/Loki optional later per ADR-007-02). Chose minimal per-dependency health + metrics emission.
- **ADR**: `ADR-007-02` records alerting backend choice (Prometheus `AlertManager` vs Grafana vs OTel alerts) and health check list `postgres/rabbitmq/redis/ai_provider/vector_store`; `ADR-007-03` records retention/purge (not in this spec's scope beyond append-only).

## Decision 6: CorrelationId propagation `X-Correlation-Id → TenantContext.CorrelationId → Activity.Baggage → DomainEvent → IntegrationEvent → AuditEntry`

- **Decision**: Middleware `CorrelationIdMiddleware` (in `Api` `Program.cs` before `UseAuthentication`) does: `if (!HttpContext.Request.Headers.TryGetValue("X-Correlation-Id", out var cid) || !Guid.TryParse(cid, out var guid)) { guid = Guid.NewGuid(); HttpContext.Response.Headers["X-Correlation-Id"] = guid.ToString(); } HttpContext.Items["CorrelationId"]=guid; TenantContext.CorrelationId=guid; Activity.Current?.SetBaggage("CorrelationId", guid.ToString()); Activity.Current?.SetTag("correlationId", guid.ToString());` Every `AppDbContextBase.SaveChangesAsync` collects `DomainEvent.CorrelationId` from `Activity.Current.Baggage` (`Activity.Current?.Baggage.FirstOrDefault(b=>b.Key=="CorrelationId")`) or `TenantContext.CorrelationId` fallback, and `IOutboxWriter.StageAsync` sets `IntegrationEvent.CorrelationId = TenantContext.CorrelationId` (via `IIntegrationEvent` interface with `CorrelationId` property — if `BuildingBlocks.EventBus` `IntegrationEvent` does not have `CorrelationId`, we add `CorrelationId` as `string` property on the concrete `*IntegrationEvent` record via inheritance or via `IntegrationEvent` `Headers` dictionary — chosen: add `CorrelationId` `Guid` to the audit-relevant `IntegrationEvent` subtypes like `DocumentApprovedIntegrationEvent` etc. via extra param `Guid CorrelationId` (non-breaking, default `Guid.Empty` if not set)). `AuditEventConsumer.HandleAsync` reads `IntegrationEvent.CorrelationId` (or `Activity.Baggage` fallback) and sets `AuditEntry.CorrelationId = thatGuid`. Every business handler that creates `AuditEntry` via consumer propagates same `CorrelationId`. `GetOperationTimeline` query does `WHERE audit.CorrelationId = @correlationId ORDER BY Timestamp asc`. Unit `CorrelationPropagationTests` asserts `HTTP X-Correlation-Id (C1) → TenantContext.CorrelationId (C1) → Activity.Baggage (C1) → DomainEvent (C1) → IntegrationEvent (C1) → AuditEntry (C1)` chain equality (end-to-end in same test with `TestServer` + `ActivitySource`).
- **Rationale**: Satisfies R3 (`Correlation IDs from OTel propagation are embedded`) + SC-004 (7-entry timeline reconstructible via `GetOperationTimeline`) + Principle XVIII (distributed operations traceable). `Activity.Baggage` is OTel standard, `AsyncLocal<TenantContext.CorrelationId>` is fallback for background jobs where `Activity.Current` may be `null` (e.g., `OutboxProcessor` background thread — it reads `TenantContext` from the `IServiceScope` created for the outbox poll). Middleware generation at request entry ensures every audit entry has a `CorrelationId` even if client omits header.
- **Alternatives considered**: Only `HttpContext.Items["CorrelationId"]` without `Activity.Baggage` (rejected — `Activity.Baggage` is OTel standard and automatically propagates to child activities/traces, while `Items` is per-request and does not survive to background `OutboxProcessor` thread); only `X-Correlation-Id` header without `Guid.NewGuid()` generation (rejected — then audit entries for header-less requests would have `Guid.Empty`, violating R1 `CorrelationId` required). Chose both `Activity.Baggage` + `TenantContext` + middleware generation.
- **ADR**: `ADR-007-03` records propagation `X-Correlation-Id → Activity.Baggage → DomainEvent → IntegrationEvent → AuditEntry` and `GetOperationTimeline` query.
